# Конвенция по описанию релизов

**Редакция 1.0, 2026-11-24.** Общая конвенция для любого продукта, у которого есть версии и люди, которые
на них обновляются: библиотека, компилятор, сервис с API, приложение. Она отвечает на вопросы «какой номер
у релиза» (§2), «как он назван и помечен» (§3), «что и где записано об изменениях» (§4–§9), «откуда берётся
черновик записи» (§10) и «что прикреплено к релизу» (§11). Как релиз собирается и выкатывается, задаёт
процесс проекта; здесь только то, что видит читатель.

Основа — три открытые спецификации, каждая закрывает свой слой: [SemVer 2.0.0](https://semver.org/) задаёт
номер версии, [Keep a Changelog 2.0.0](https://keepachangelog.com/en/2.0.0/) — записи об изменениях,
[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) — коммиты, из которых записи
собираются. Формального стандарта на описание релизов нет, и Keep a Changelog называет себя одним продуманным
мнением, а не стандартом. Но, по оценке самого проекта, его называют своим форматом десятки тысяч open-source
проектов, и на него опираются инструменты автоматизации, поэтому здесь он принят целиком. Добавлено только
то, чего в нём нет: язык текста, тег и заголовок релиза, черновик от инструментов и моделей, файлы релиза,
отозванная версия.

Правила сформулированы так, чтобы их можно было проверить: скриптом по `CHANGELOG.md`, по тегу и по странице
релиза, глазами на ревью описания. Каждое правило снабжено причиной. Отклонение возможно, но только
записанное (§13), с причиной и ценой; «у нас так принято» причиной не считается. «Misc improvements» в роли
записи, ломающее изменение без пометки, номер, не соответствующий содержимому, строка внутреннего реестра
вместо ссылки — любого из этого достаточно, чтобы вернуть описание на ревью.

## 0. Принципы

1. **Запись пишется тому, кто обновляется.** Читатель решает три вопроса: обновляться, что сломается, что
   делать. Автор изменения эти вопросы уже решил; ему интересно «что сделано», читателю — только «что
   изменилось для меня».
2. **Заметное, а не всё.** Коммит — шаг в истории кода, запись — заметная разница, часто поверх нескольких
   коммитов. Полный перечень изменений уже есть, это история версий; журнал, куда свалено всё, не читают.
3. **Форма у каждого релиза одна.** Шесть категорий, один порядок, одни заголовки. Читатель осваивает форму
   один раз и дальше находит нужное глазами, а не чтением.
4. **Что требует действия — выше остального.** Уязвимость, удаление, ломающее изменение требуют от читателя
   действия, новое — только внимания. Первое в тексте стоит выше второго.
5. **Источник — файл в репозитории, а не страница на хостинге.** Файл переезжает вместе с кодом на любой
   хостинг и читается офлайн; страница релиза живёт в базе хостинга и при переезде остаётся там.
6. **Машина готовит черновик, человек отбирает и читает.** Генератор или модель собирают материал за
   секунды; решить, что заметно читателю, и написать это понятно может только человек.
7. **Вышедшая версия не меняется.** Дефект опубликованной версии исправляется новой версией, плохая версия
   отзывается с пометкой, а не затирается.
8. **Текст простой.** Читатель часто не носитель языка текста: короткие предложения, обычные слова, без
   внутренней иронии.

## 1. Коммит, changelog, описание релиза

| Артефакт | Что это | Где живёт | Пишется для кого |
|---|---|---|---|
| коммит | шаг в истории кода | история репозитория | для тех, кто читает историю |
| changelog | полный перечень заметных изменений по каждой версии | `CHANGELOG.md` в репозитории | для пользователей |
| описание релиза | объявление одного релиза | страница релиза на хостинге | для пользователей |

Changelog — источник, описание релиза — его производное. При выпуске раздел версии копируется на страницу
релиза целиком и расширяется только тем, что анонсу нужно сверх записи: шагами перехода и файлами. Два
текста, которые пишутся порознь, расходятся к третьему релизу, и читатель не знает, какому верить.

## 2. Номер версии

**Норма.** Версия пишется по SemVer, `MAJOR.MINOR.PATCH`, всегда тремя числами. Какая цифра растёт,
определяет самое сильное изменение в релизе:

| Что вошло в релиз | с 1.0.0 | в линии 0.Y.Z |
|---|---|---|
| несовместимое изменение | MAJOR | MINOR |
| новая функциональность, объявление устаревшим | MINOR | MINOR |
| только исправления | PATCH | PATCH |

Линия `0.Y.Z` — начальная разработка: по SemVer (п. 4) в ней всё может измениться в любой момент, и
публичный контракт не считается стабильным. Границу совместимости в ней задаёт MINOR. Так линию читают
менеджеры пакетов: `^0.2.3` в npm и требование `0.2.3` в Cargo означают `>=0.2.3 <0.3.0`. Поэтому
несовместимое изменение в этой линии поднимает MINOR, а PATCH не несёт его никогда.

Суффикс `-rc.1`, `-rc.2` (`1.0.0-rc.1`) — кандидат одной конкретной версии. Кандидат публикуется отдельным
релизом с флагом prerelease (§3); число кандидата только растёт; кандидат предшествует своей версии
(`1.0.0-rc.1 < 1.0.0`).

Нестабильность отмечается одним способом. Линия, у которой стабильного контракта ещё нет, нумеруется
`0.Y.Z`, а слово канала (`alpha`, `beta`) идёт в заголовок релиза, не в номер. Суффикс остаётся кандидатам.
Две метки говорят одно и то же, а вторая ещё и выбивает версию из диапазона зависимостей: требование
`^0.1.7` не подтянет `0.1.7-alpha.1`. Метаданные сборки (`+…`) в номере релиза не используются: при
сравнении версий они игнорируются (SemVer, п. 10), и две сборки оказались бы одной версией.

**Версия одна во всех местах:** тег, заголовок релиза, заголовок раздела changelog, имена файлов и то, что
продукт сообщает о себе (`--version`, `User-Agent`, «О программе»). Все берутся из одного файла версии в
репозитории. Пять чисел, проставленных руками, расходятся, и читатель видит три версии одного релиза.
Проверяемая форма: сборка релиза падает, если `git describe --tags --exact-match` не совпадает с версией,
которую сообщает продукт.

**Контракт объявлен.** SemVer требует объявить публичный контракт, к которому относятся обещания номера.
Шапка changelog называет его одним предложением: командная строка и коды выхода, API библиотеки, язык,
форматы файлов, схема конфигурации, протокол. Без этого «ломающее изменение» пустое слово: удаление флага
для одного продукта ломает командную строку, для другого — нет.

Верно: `2.3.0` у релиза с новой функцией; `2.2.1` у релиза только с исправлениями; `1.0.0-rc.1` у
кандидата; `0.4.0` у несовместимого изменения в линии `0.Y.Z`.
Неверно: `2.3`; `2.3.0-hotfix`; `2.3.0.1`; `0.1.7-alpha.1`; `2.2.1` у релиза с несовместимым изменением.

## 3. Тег, заголовок, метки

- **Тег аннотированный и стоит на вышедшем коммите:** `v2.3.0`. `v` — приставка тега, не часть номера
  (SemVer, FAQ). Несколько независимо версионируемых продуктов в одном репозитории различаются приставкой
  с именем продукта: `oracle-v0.1.7`. Других слов в теге нет: `-final`, `-hotfix` и `-release` дублируют то,
  что уже сказано номером и флагом.
- **Тег не двигается и не используется повторно** (§12).
- **Заголовок релиза** — `<Продукт> <версия>`; слово канала ставится в скобки: `<Продукт> 0.1.7 (alpha)`.
  Кодовое имя, если оно у продукта есть, идёт после номера в кавычках. «Release», «Final» и восклицательные
  знаки в заголовок не входят.
- **Флаг prerelease ставится линии `0.Y.Z` и кандидатам; `Latest` получает только последний стабильный
  релиз.** Установщик, который следует за `latest`, не должен получить кандидата.
- **Текст не повторяет заголовок.** Хостинг показывает заголовок над текстом, и вторая строка того же
  содержания даёт на странице два названия. Заголовок раздела changelog при переносе на страницу выпадает:
  его заменяет поле заголовка.
- **Дата публикации** ставится в changelog в ISO `YYYY-MM-DD`: та же форма, что у дат
  [в конвенции по БД](database.md). На странице релиза дату ставит хостинг.

## 4. Файл changelog

Файл называется `CHANGELOG.md` и лежит в корне репозитория: предсказуемое имя ищут, не читая README.
Несколько независимых продуктов в одном репозитории ведут по файлу каждый; у продукта из многих частей с
собственными changelog частей есть ещё один, центральный и сводный.

Файл открывается шапкой, которая называет формат, схему нумерации и контракт, покрываемый номером (§2):

```markdown
# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
The version covers the command line and exit codes.
```

Ссылка на Keep a Changelog закреплена за редакцией: корневая ссылка сайта открывает более старую страницу,
и обещание «формата по ссылке» перестаёт быть точным.

- **Раздел на каждую вышедшую версию**, включая кандидатов и отозванные; новые сверху.
- **Заголовок раздела** — `## [2.3.0] - 2026-11-24`. Номер в квадратных скобках — ссылка, которую
  разрешают один раз в конце файла: каждая версия ведёт на сравнение с предыдущей, `[Unreleased]` — на
  сравнение последнего тега с `HEAD`, первая версия — на свой тег. Так каждая версия привязана к тегу и к
  точному перечню того, что изменилось, а заголовок остаётся чистым.
- **`## [Unreleased]` над всеми** собирает то, что вошло после последнего релиза. При выпуске он
  переименовывается в номер, в заголовке и в ссылке, и сверху появляется новый пустой.
- **Пустые секции не пишутся.**
- **Все заметные изменения на месте, мелкие опущены.** Неполный changelog вводит так же, как отсутствие:
  читатель считает его полной картиной.
- **Раздел может открываться одним-двумя предложениями** о теме релиза; у небольшого релиза их нет.
- **При переходе на новую редакцию формата прошлые записи не переписываются**; переход отмечается в том
  релизе, с которого действует.
- **Выросший файл** переносит старые версии в отдельные файлы со ссылками в обе стороны. Записи не
  удаляются: кто-то всё ещё обновляется со старой версии.
- **Частые конфликты слияния** снимаются `merge=union` для `CHANGELOG.md` в `.gitattributes`; при большом
  потоке записи держат фрагментами в `changelog.d/` и собирают в файл при выпуске.

## 5. Структура описания релиза

```markdown
<Одно-два предложения: тема релиза, уровень стабильности.>

## Upgrading
<Шаги перехода — только если в релизе есть ломающие изменения.>

## Security
## Removed
## Changed
## Deprecated
## Fixed
## Added
## Known issues
<Что не работает, обходной путь, ссылка — только если ограничения есть.>

## Artifacts
<Файлы, чем собраны, как проверить (§11).>

**Full changelog:** <ссылка на сравнение с предыдущей версией>
```

- **Порядок категорий фиксирован и не меняется от релиза к релизу.** Он идёт по срочности: что требует от
  читателя действия — уязвимость, удаление, изменение поведения, — стоит выше того, что просто приятно
  узнать. Если первыми идут новые возможности, исправление уязвимости заметить труднее.
- **Пустые секции опускаются.** Запись полная (§4), поэтому отсутствие секции читается как «изменений
  такого рода нет».
- **Внутри секции первым — самое важное для читателя.**
- **Область — не категория.** Часть продукта (CLI, парсер, стандартная библиотека) называется в начале
  записи (`- Parser: …`) или подзаголовком на уровень ниже категории, но никогда на уровне категорий. Список
  областей закрыт и одинаков во всех релизах; имя области добавляется, когда оно сообщает то, чего нет в
  самой записи.
- **Уровни заголовков.** В файле версия — `##`, категория — `###`, область — `####`. На странице релиза
  заголовок версии заменён полем заголовка, поэтому всё стоит на уровень выше.
- **Язык один на все релизы** — язык публичной документации продукта. Второй язык — отдельный перевод, а не
  вторые предложения внутри записи. Названия категорий не переводятся по месту: это шесть слов Keep a
  Changelog либо их закреплённые эквиваленты (`Добавлено`, `Изменено`, `Устарело`, `Удалено`, `Исправлено`,
  `Безопасность`), один набор на продукт.
- **Благодарности контрибьюторам — по желанию,** отдельной секцией в конце и коротко: имя или ссылка на
  профиль переживают смену хостинга, а `@handle` — нет.

## 6. Категории

Категорий шесть, и набор закрыт. Категория отвечает на вопрос «что это за изменение»; почему оно важно,
говорит текст записи, а не новая категория.

| Категория | Признак | В записи обязательны |
|---|---|---|
| `Security` | закрыта уязвимость | идентификатор (`CVE-…`, `GHSA-…`) первым словом; затронутые версии; ссылка на бюллетень |
| `Removed` | функциональности больше нет | что использовать вместо; начиная с какой версии она была устаревшей |
| `Changed` | существовало, работало как задумано, теперь работает иначе | что именно теперь иначе; для производительности — число и условия замера |
| `Deprecated` | пока работает, будет удалена | замена; версия, в которой состоится удаление |
| `Fixed` | поведение было неверным, теперь верно | симптом: при каком действии что происходило |
| `Added` | раньше этого не существовало | что стало возможно |

Сомнение между `Fixed`, `Changed` и `Security` снимается одним вопросом: прежнее поведение было ошибкой?
Было — `Fixed`. Оно задумано и меняется — `Changed`. Закрыта уязвимость — `Security`, даже если по виду это
исправление: у неё другие срочность и читатель.

Запись `Security` — короткое описание для человека, а не бюллетень; затронутые версии, степень тяжести и
исправление читатель находит по ссылке.

**Что категорией не становится:**

- `Performance`, `Improved`, `Enhanced` — это `Changed`: «Переписан парсер JSON, импорт в три раза быстрее»
  изменяет существующее поведение.
- `New` — это `Added`.
- `Internal`, `Housekeeping`, `Refactoring`, `CI`, `Tests`, `Chores` — не записываются вовсе: читателю они
  разницы не дают. Исключение одно: изменение, которое читатель видит (новое руководство, изменившийся
  диагностический текст), идёт в свою категорию.
- `Dependencies` — по эффекту обновления: незаметное не записывается, исправление — в `Fixed`,
  несовместимое — в `Changed` с пометкой `**Breaking:**`.
- `Breaking` — не категория, а пометка в записи (§8).
- `Known issues` — не изменение: ограничения обнаружены, а не изменены (§9).
- Имена частей продукта — области внутри категории (§5).

## 7. Запись

Запись — один пункт списка: одно-два предложения о продукте после обновления. Примеры даны на английском;
на другом языке действуют те же правила.

- **Одна запись — одно заметное изменение.** Десять коммитов, которые вместе дают одну разницу для
  пользователя, — одна запись; коммит, который разницы не даёт, — ноль записей.
- **Сказано, что теперь иначе и что это читателю даёт.** «Поддержка портов» называет тему; «Приложение
  слушает порт, заданный в настройках, а не первый свободный» — разницу.
- **Внутренние имена — только те, что видит пользователь.** Модуль, функция, класс, номер задачи и имя
  ветки остаются в истории коммитов. Видит он команды, опции, коды ошибок, имена API, файлы и сообщения;
  они пишутся ровно так, как их вводит пользователь, кодовым выделением.
- **Исправление описывается симптомом.** Читатель ищет в списке свою проблему: при каком действии что
  происходило. Внутренняя причина — вторым предложением, и только если помогает понять, затронула ли
  неисправность читателя (платформа, объём, режим).
- **Числа — с условиями замера.** «В три раза быстрее» значит «на импорте миллиона записей: было 41 с,
  стало 13 с». Число без условий — то же оценочное слово.
- **Ссылка — когда помогает.** На задачу, запрос на слияние, бюллетень, пункт спецификации. Ссылка должна
  открываться у читателя описания: строка внутреннего реестра, номер без ссылки и путь к закрытому
  документу — не ссылки. Ссылка стоит в записи, к которой относится, а не общим списком в конце.
- **Без оценки.** «Улучшено», «оптимизировано», «повышена стабильность», «мелкие исправления» — не записи:
  по ним не понять, затронула ли разница читателя.
- **Без процесса и исполнителя.** «Мы добавили», «в рамках задачи 1234», «проведён рефакторинг» описывают
  работу, а не продукт.
- **Коротко.** Одна-две строки; длинное объяснение живёт по ссылке. Иллюстрация уместна там, где изменение
  видно глазом (интерфейс): один снимок или короткая запись экрана.

Верно:

```markdown
- `build --watch` no longer hangs when stdin is closed (#1234).
- Export to PDF now keeps vector diagrams; the file stays editable in the editor.
- Parser: recover from a missing final chunk instead of raising (#1250).
- Rewrote the JSON parser; importing 1 000 000 records takes 13 s instead of 41 s.
```

Неверно:

```markdown
- Misc improvements and bug fixes.
- Refactored `ExportService`, upgraded `pdfgen` to 4.2.
- Fixed bug 1234.
- Significantly faster JSON parsing.
- Closed rows 1986–1990 of the internal defect registry.
```

## 8. Ломающие изменения и устаревание

- **Ломающее изменение помечается в самой записи:** `**Breaking:**` первым словом. Запись остаётся в своей
  категории, обычно `Changed` или `Removed`, и идёт в ней первой. Отдельной секции нет: кто просматривает
  `Changed` или `Removed`, видит эти записи на месте, а отдельная секция заставляет искать одно изменение
  в двух местах.
- **Запись называет, что ломается, кого затрагивает и что сделать.** Короткая инструкция остаётся в записи
  («переименуйте опцию `color` в `theme`»); длинная живёт в руководстве по миграции, и на неё стоит ссылка.
  Процедура на сорок строк хоронит перечень изменений и превращает журнал в инструкцию.
- **На странице релиза шаги перехода вынесены в `Upgrading`** над категориями — единственное место, где
  процедура написана целиком.
- **Номер следует изменению:** MAJOR, в линии `0.Y.Z` — MINOR; PATCH не несёт ломающего изменения никогда.
- **Устаревание объявляется раньше удаления.** В одном релизе функциональность помечается `Deprecated`, и
  только в более позднем — `Removed`. Запись `Deprecated` называет замену и версию удаления; запись
  `Removed` — замену и версию, начиная с которой функциональность была устаревшей. Кто обновляется через
  версию, встречает предупреждение раньше, чем теряет функциональность.

Если в описании не записано ничего другого, записаны хотя бы устаревания, удаления и ломающие изменения.

## 9. Известные ограничения

- **Известные ограничения — не категория изменения:** они обнаружены, а не изменены. Это необязательная
  секция `Known issues` в конце раздела версии.
- **Каждое ограничение** называет: что не работает, при каком условии, обходной путь, ссылку на задачу, в
  которой оно отслеживается.
- **Список повторяется целиком в каждой следующей версии, где ограничения действуют.** «Без изменений,
  см. 0.1.5» отправляет читателя по цепочке страниц, а он открывает страницу своего релиза.
- **Исправленное ограничение** уходит из списка и появляется в `Fixed` того релиза, где исправлено.
- **Секции нет — известных ограничений на момент публикации нет.**

## 10. Черновик от инструментов и моделей

Генератор из коммитов (semantic-release, release-please, Changesets, git-cliff),
[генератор хостинга](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)
(GitHub собирает слитые запросы на слияние по меткам из `.github/release.yml`) и языковая модель, которой
дали diff, выдают черновик. Черновик — исходный материал, а не текст к публикации.

Причина. Коммит и запись пишутся разным людям. Многие коммиты читателю безразличны; то, что ему важно, часто
разложено по нескольким коммитам и требует пересказа с его точки зрения. Сортировка по типу сокращает
список, но точку зрения не меняет.

- **Коммиты по Conventional Commits** дают черновику структуру: `feat` — кандидат в `Added` и в MINOR, `fix` —
  в `Fixed` и в PATCH, `!` или футер `BREAKING CHANGE:` — в ломающие. Заголовок запроса на слияние пишется
  для того, кто будет обновляться: это будущий коммит и исходник будущей записи. Слияние squash: одно слитое
  изменение — один коммит.
- **Модель получает то же задание, что и контрибьютор**, и задание записывается туда, где его прочитают
  агенты (`AGENTS.md`, `CLAUDE.md`): перечислить заметные изменения, видимые пользователю; не вставлять
  журнал коммитов; отнести каждое изменение к одной из шести категорий; объяснить причину в тексте; пометить
  ломающие; убрать то, что не стоит чтения.
- **Черновик прочитан человеком до того, как его увидит кто-либо ещё.** Прочтение идёт по чек-листу (§14), а
  не просмотром: беглый текст, который никто не читал, теперь стоит секунды.
- **Полнота сверена по диапазону.** Открыт диапазон от предыдущего тега до нового; каждое слитое изменение
  либо имеет запись, либо осознанно отброшено по признакам §1 и §6.
- **CI делает механику:** переносит `Unreleased` в датированную версию, проверяет формат файла, напоминает
  о записи. Правка changelog не назначается обязательной проверкой на каждое изменение: под угрозой красной
  сборки строку добавляют ради прохождения, и журнал заполняется шумом. Отбор остаётся за человеком.

## 11. Страница релиза и файлы

Релиз на хостинге — тег, текст и файлы. Текст — раздел версии из `CHANGELOG.md` плюс то, что есть только на
странице: блок `Upgrading`, блок `Artifacts` и ссылка на полный changelog.

- **Публикация идёт по порядку:** аннотированный тег, черновик релиза, текст, файлы с контрольными суммами,
  проверка флагов, публикация. После публикации релиз неизменяем: у GitHub с включёнными
  [immutable releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)
  тег и файлы релиза не меняются и не удаляются. Незавершённый релиз нельзя дописать, а подписчики видят
  релиз в момент публикации.
- **Файлы** — по одному на поддерживаемую платформу с именем
  `<продукт>-<версия>-<ОС>-<архитектура>.<формат>`; `SHA256SUMS` на все прикреплённые архивы, посчитанные по
  загруженным файлам; исходники — у открытых продуктов; подпись — там, где пользователи проверяют подпись.
- **Проверка для пользователя — одной командой, и она написана на странице:** `sha256sum -c SHA256SUMS`.
- **Блок `Artifacts`** называет: коммит тега, чем собрано (рабочий процесс и его запуск), что проверено
  перед публикацией и с каким результатом. Пишется только то, что выполнялось; числа — с условиями (§7).
- **Релиз создаётся командой** с существующим тегом:

  ```sh
  gh release create v2.3.0 --verify-tag --title "<Продукт> 2.3.0" --notes-file release.md <файлы>
  ```

  `--verify-tag` обязателен: без него при отсутствующем теге `gh` создаёт тег на вершине ветки по
  умолчанию, и релиз прикрепляется к чужому коммиту. Для линии `0.Y.Z` и кандидатов добавляется
  `--prerelease`.
- **Ссылка на полный changelog** — сравнение предыдущего тега с новым:
  `<хостинг>/<владелец>/<репозиторий>/compare/<старый>...<новый>`.
- **Релиз с исправлением уязвимости выходит вместе с бюллетенем** (security advisory): changelog его не
  заменяет.

## 12. Отозванная и исправленная версия

- **Содержимое вышедшей версии не меняется** (SemVer, п. 3): дефект в бинарном файле исправляется новой
  версией, а не перезаливкой файла.
- **Отозванная версия остаётся в списке с пометкой.** Версию, отозванную из-за серьёзного дефекта или
  уязвимости, не удаляют: `## [2.3.0] - 2026-11-24 [YANKED]`. На странице релиза пометка идёт в заголовок,
  а текст открывается причиной отзыва и версией, на которую перейти. Тег не удаляется и не используется
  повторно: кто установил версию, находит её с пометкой, а инструмент, уже видевший тег, не встречает его
  на другом коммите.
- **Пропущенная запись добавляется после публикации**, и дата правки ставится рядом, чтобы читатель заметил
  изменение.

## 13. Отклонения

Отклонение от правила допустимо, если записано в документе продукта (раздел «Отклонения от конвенции по
описанию релизов») таблицей: правило, что сделано иначе, почему, цена и условие, при котором отклонение
снимается. Типичные законные отклонения:

- changelog только на страницах релизов хостинга, а `CHANGELOG.md` — со ссылкой на них, у небольшого
  продукта на одном хостинге; цена — история не переезжает вместе с кодом;
- календарная нумерация (`2026.11.1`) вместо SemVer у продукта, который выходит по расписанию; схема
  нумерации объявляется в шапке changelog;
- непрерывная поставка без номеров версий — записи с датами под `Unreleased`;
- седьмая категория, когда продукт доказал, что шести мало; это бывает редко.

Отклонение без записи блокер ревью описания релиза.

## 14. Чек-лист перед публикацией

```markdown
- [ ] Номер соответствует содержимому: несовместимое — MAJOR (в 0.Y.Z MINOR), новая функциональность — MINOR, только исправления — PATCH
- [ ] Версия одна в теге, заголовке, шапке раздела changelog, именах файлов и в том, что сообщает продукт
- [ ] Тег аннотированный, v<X.Y.Z> (или <продукт>-v<X.Y.Z>), стоит на вышедшем коммите и не двигался
- [ ] Флаг prerelease у линии 0.Y.Z и у кандидатов; Latest — у последнего стабильного релиза
- [ ] Заголовок <Продукт> <версия> со словом канала в скобках; текст заголовок не повторяет
- [ ] В CHANGELOG.md раздел ## [<X.Y.Z>] - <YYYY-MM-DD> новее остальных, со ссылкой на сравнение с предыдущей версией; над ним пустой Unreleased
- [ ] Категории только из шести, в фиксированном порядке; пустые секции отсутствуют; области — внутри категорий
- [ ] Каждое ломающее изменение помечено **Breaking:**, стоит первым в своей категории; на странице есть блок Upgrading
- [ ] Каждое устаревание называет замену и версию удаления; удаление идёт отдельным, более поздним релизом
- [ ] Записи Security начинаются с идентификатора уязвимости и ведут на бюллетень; бюллетень опубликован
- [ ] У каждой записи сказано, что теперь иначе и что это даёт читателю; числа — с условиями замера
- [ ] В записях нет внутренних имён, которых не видит пользователь, и ссылок, которые у читателя не открываются
- [ ] Нет записей вида «улучшено», «исправления», «стабильность» без содержания
- [ ] Известные ограничения перечислены полностью, с обходным путём и ссылкой
- [ ] Диапазон от предыдущего тега до нового пройден: каждое слитое изменение либо записано, либо осознанно отброшено
- [ ] Черновик от инструмента или модели прочитан человеком по этому чек-листу
- [ ] Файлы приложены на каждую поддерживаемую платформу; SHA256SUMS покрывает все файлы и проверена
- [ ] Релиз создан из черновика с существующим тегом; флаги проверены до публикации
- [ ] Каждое отклонение записано в таблице продукта с причиной, ценой и условием снятия
```

The version covers the command line, exit codes and the project file format.

## [Unreleased]

Synchronization of large projects is faster; `--legacy-sync` is deprecated.

### Changed

- Synchronizing a project of 10 000 files takes 8 s instead of 25 s.

### Deprecated

### Fixed

- Export to PDF no longer drops diagrams when the project was opened from a network share ([#889](https://github.com/example/product/pull/889)).
