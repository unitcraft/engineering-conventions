# Конвенция по описанию релизов

**Редакция 1.1, 2026-11-28.** Пишите описание релиза для человека, который решает, обновлять ли
продукт. Читателю нужно понять, что изменится после обновления и какие действия потребуются.

Применяйте конвенцию к библиотекам, компиляторам, сервисам с API и приложениям, у которых есть
версии и пользователи. Процесс проекта определяет порядок сборки и развёртывания. Эта конвенция
задаёт номер версии, тег, содержание страницы релиза и состав файлов для скачивания.

Для нумерации используйте [SemVer 2.0.0](https://semver.org/).
Журнал изменений ведите по [Keep a Changelog 2.0.0](https://keepachangelog.com/en/2.0.0/).
При подготовке черновика используйте типы коммитов из [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).
Русский текст редактируйте по [конвенции по техническому письму](technical-writing.md).

## 0. Принципы

1. Опишите последствия обновления. Читатель должен узнать, затронет ли его изменение и что ему делать.
2. Включите все изменения, которые заметит пользователь. Несколько коммитов могут дать одну запись.
3. Во всех релизах используйте одни названия категорий и один порядок (§5–6). Так читатель найдёт
   нужную запись на знакомом месте.
4. Выше ставьте изменения, которые требуют действий. Исправление уязвимости, удаление функции
   или изменение поведения читатель должен увидеть раньше новой возможности.
5. Храните журнал изменений в репозитории. Тогда история доступна офлайн и переезжает вместе с кодом.
6. Если черновик подготовил инструмент или модель, поручите редактору отбор записей и проверку текста (§10).
7. Если опубликованная версия содержит дефект, выпустите исправление под новым номером. При отзыве
   версии сохраните запись о ней (§12).
8. Используйте короткие предложения и знакомые читателю слова. Избегайте шуток, понятных только команде.

Проверьте файл `CHANGELOG.md`, тег и страницу релиза. Если номер расходится с содержанием,
верните описание на доработку. Так же поступите, если пропущена пометка о несовместимости,
запись содержит только общую оценку или ссылка недоступна читателю. Отклонения оформляйте по §13.

## 1. Коммит, changelog, описание релиза

| Документ или запись | Для кого | Что содержит |
|---|---|---|
| Коммит в репозитории | Для тех, кто изучает историю кода | Один шаг разработки. |
| Журнал изменений (changelog) в `CHANGELOG.md` | Для пользователей продукта | Все заметные изменения по версиям. |
| Описание релиза на хостинге | Для тех, кто обновляется до этой версии | Изменения одной версии, шаги перехода и файлы релиза. |

Используйте журнал как источник. При выпуске скопируйте на страницу релиза весь текст раздела
версии. Оформите заголовок по §3, добавьте шаги перехода, сведения о файлах и ссылку на сравнение
тегов (§11). Так читатель получит одинаковое описание изменений в обоих местах.

## 2. Номер версии

В начале журнала одним предложением определите публичный контракт продукта. Это могут быть команды
и коды выхода, API библиотеки, язык, форматы файлов, схема конфигурации или протокол. По этому
контракту читатель определяет, совместима ли новая версия с его способом использования продукта.

Записывайте номер тремя числами в формате `MAJOR.MINOR.PATCH`. При выборе номера найдите
первую подходящую строку таблицы.

| Что вошло в релиз | Какую часть номера увеличить с `1.0.0` | Какую часть увеличить в линии `0.Y.Z` |
|---|---|---|
| Изменение, несовместимое с публичным контрактом | MAJOR | MINOR |
| Новая функция или объявление об устаревании | MINOR | MINOR |
| Только исправления | PATCH | PATCH |

**Начальная разработка.** По п. 4 SemVer публичный контракт линии `0.Y.Z` ещё может меняться.
В этой линии границу совместимости задаёт MINOR. Например, для `^0.2.3` в npm и `0.2.3` в Cargo
диапазон версий — `>=0.2.3 <0.3.0`. Несовместимое изменение требует нового MINOR даже в линии `0.Y.Z`.

**Предварительные версии.** Если контракт ещё нестабилен, используйте номер `0.Y.Z`. Укажите
канал `alpha` или `beta` в заголовке. Суффикс в номере меняет подбор зависимостей. Например,
`0.1.7-alpha.1` не попадает в диапазон `^0.1.7`.

Суффиксы `-rc.1`, `-rc.2` используйте только для кандидатов конкретной версии. Каждого кандидата
выпускайте отдельным предварительным релизом с флагом `prerelease`. Увеличивайте порядковый номер
кандидата. Пример порядка версий — `1.0.0-rc.1 < 1.0.0`.

Исключите метаданные сборки (`+…`) из номера релиза. По п. 10 SemVer эти данные не влияют на
порядок версий.

**Единый источник номера.** Храните номер версии в одном файле репозитория. Используйте его
в теге, заголовке релиза, заголовке раздела журнала, именах файлов и самом продукте
(`--version`, `User-Agent`, «О программе»). При сборке получите тег командой
`git describe --tags --exact-match`. Если номер в теге расходится с номером, который сообщает
продукт, завершите сборку релиза с ошибкой.

| Пример | Когда применять |
|---|---|
| `2.3.0` | В версии появилась новая функция. |
| `2.2.1` | В версию вошли только исправления. |
| `1.0.0-rc.1` | Готов первый кандидат версии `1.0.0`. |
| `0.4.0` | В линии `0.3.Z` изменился публичный контракт с потерей совместимости. |

Отклоняйте номера `2.3`, `2.3.0-hotfix`, `2.3.0.1` и `0.1.7-alpha.1`.
Если релиз нарушает совместимость, номер исправления `2.2.1` ему также не подходит.

## 3. Тег, заголовок, метки

- Создайте аннотированный тег на коммите, из которого собран релиз. Используйте формат `v2.3.0`.
  Буква `v` входит только в тег. Если в репозитории несколько продуктов с независимой нумерацией,
  добавьте имя продукта, например `oracle-v0.1.7`. Исключите суффиксы `-final`, `-hotfix` и `-release`.
- Сохраняйте опубликованный тег на исходном коммите. Повторное использование тега запрещено (§12).
- Используйте заголовок `<Продукт> <версия>`. Канал укажите в скобках, например `<Продукт> 0.1.7 (alpha)`.
  Если у релиза есть кодовое имя, поставьте его в кавычках после номера. Опустите слова
  «Release», «Final» и восклицательные знаки.
- Для линии `0.Y.Z` и для кандидатов установите флаг `prerelease`. Метку `Latest` назначайте только
  последнему стабильному релизу. Установщики могут выбирать версию по этой метке.
- При переносе раздела журнала на страницу релиза опустите заголовок раздела. Хостинг уже
  показывает название релиза над текстом.
- В журнале укажите дату публикации в формате `YYYY-MM-DD`. На странице релиза дату указывает хостинг.
  [Формат календарных дат](database.md)

## 4. Файл changelog

Разместите `CHANGELOG.md` в корне репозитория. Если в репозитории несколько независимых продуктов,
ведите журнал для каждого. Если части одного продукта ведут свои журналы, добавьте сводный журнал продукта.

В начале файла укажите формат журнала, схему нумерации и публичный контракт (§2).
Сошлитесь на конкретную редакцию Keep a Changelog, чтобы читатель открыл нужное описание формата.

```markdown
# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
The version covers the command line and exit codes.
```

- Создайте раздел для каждой выпущенной версии, включая кандидатов и отозванные версии. Ставьте
  новые версии выше старых. Используйте заголовок вида `## [2.3.0] - 2026-11-24`.
- В конце файла определите ссылку для каждого номера в квадратных скобках. Для первой версии
  укажите ссылку на тег. Для каждой следующей — на сравнение её тега с предыдущим.
- Вверху ведите раздел `## [Unreleased]` для изменений после последнего релиза. Ссылка
  `[Unreleased]` ведёт на сравнение последнего тега с `HEAD`.
- При выпуске замените `Unreleased` номером версии в заголовке и определении ссылки.
  Добавьте дату в заголовок. Создайте сверху новый пустой раздел `Unreleased` и обновите его ссылку.
- Включите все заметные изменения. Опускайте мелкие изменения и пустые категории.
  В начале раздела можно описать тему релиза в одном-двух предложениях. Для небольшого релиза опустите введение.
- Если формат журнала изменился, отметьте переход в первом релизе с новым форматом. Сохраните
  прежние записи в исходном виде.
- Если журнал стал слишком большим, перенесите старые версии в отдельные файлы. Добавьте ссылки
  в обе стороны. Сохраните историю для тех, кто обновляется со старых версий.
- Если при слиянии часто возникают конфликты, задайте `merge=union` для `CHANGELOG.md` в `.gitattributes`.
  При большом потоке изменений храните записи отдельными фрагментами в `changelog.d/`
  и собирайте их в журнал при выпуске.

## 5. Структура описания релиза

Расположите разделы страницы в порядке, указанном в шаблоне. Опускайте пустые разделы.
В каждой категории ставьте первой запись, которая важнее всего для читателя (§8).

```markdown
<Одно-два предложения: тема релиза, уровень стабильности.>

## Upgrading
<Шаги перехода — только если в релизе есть ломающие изменения.>

## Security
## Removed
## Changed
## Deprecated
## Fixed
## Added
## Known issues
<Что не работает, обходной путь, ссылка — только если ограничения есть.>

## Artifacts
<Файлы, чем собраны, как проверить (§11).>

**Full changelog:** <ссылка на сравнение с предыдущей версией>
```

Часть продукта можно указать в начале записи (`- Parser: …`) или в подзаголовке внутри категории.
Используйте закрытый список областей для всех версий. Добавляйте область только тогда, когда
она помогает понять, к чему относится изменение. Примеры областей — командная строка (CLI),
парсер и стандартная библиотека.

В журнале используйте `##` для версии, `###` для категории и `####` для области. На странице
релиза название версии уже стоит в поле заголовка. Поднимите категорию и область на один уровень.

Пишите все релизы на языке публичной документации продукта. Если нужен второй язык, выпустите
отдельный перевод. Выберите один набор названий категорий для всего продукта. Можно использовать
английские названия из §6 или закрепить русские в том же порядке — `Безопасность`, `Удалено`,
`Изменено`, `Устарело`, `Исправлено`, `Добавлено`.

По желанию поблагодарите участников в коротком разделе в конце. Укажите имя или ссылку на профиль.
При смене хостинга упоминание вида `@handle` может перестать работать.

## 6. Категории

Для каждой записи выберите одну из шести категорий. В тексте объясните последствия изменения.

| Категория | Когда выбрать | Что указать |
|---|---|---|
| `Security` | Исправлена уязвимость | Начните с идентификатора (`CVE-…`, `GHSA-…`). Назовите затронутые версии и дайте ссылку на бюллетень. |
| `Removed` | Возможность удалена | Укажите замену и версию, в которой объявили об устаревании. |
| `Changed` | Изменилось предусмотренное поведение | Опишите новое поведение. Для изменения производительности приведите результат и условия замера. |
| `Deprecated` | Возможность пока доступна, удаление запланировано | Укажите замену и версию удаления. |
| `Fixed` | Исправлена ошибка в поведении продукта | Опишите действие пользователя и наблюдаемый симптом. |
| `Added` | Появилась новая возможность | Объясните, что теперь может сделать пользователь. |

Если исправлена уязвимость, выберите `Security`. Дайте краткое описание. Подробности о затронутых
версиях, степени тяжести и исправлении читатель найдёт в бюллетене. Для остальных исправлений
выберите `Fixed`. Если прежнее поведение соответствовало замыслу, используйте `Changed`.

Применяйте те же категории к изменениям, которые при разработке называют иначе.

- Улучшения производительности (`Performance`, `Improved`, `Enhanced`) отнесите к `Changed`.
  Для новой возможности (`New`) используйте `Added`.
- Для изменений с метками `Internal`, `Housekeeping`, `Refactoring`, `CI`, `Tests` и `Chores`
  включайте только видимый пользователю результат. Например, для нового руководства или изменённого
  сообщения диагностики выберите категорию по результату.
- Для обновления зависимостей (`Dependencies`) также оцените результат. Пропустите незаметное
  обновление. Исправление отнесите к `Fixed`, а несовместимое изменение — к `Changed`
  с пометкой `**Breaking:**`.
- Несовместимость обозначьте пометкой в записи (§8). Известные ограничения вынесите в `Known issues` (§9).
  Названия частей продукта используйте как области внутри категории (§5).

## 7. Запись

Оформите каждое заметное изменение одним пунктом списка. Уложитесь в одно-два предложения
на одной-двух строках. Если несколько коммитов дали один результат, объедините их в одной записи.
Если результат виден только разработчикам, пропустите запись.

- Назовите действие пользователя и результат после обновления. Например, «Теперь приложение
  слушает порт, указанный в настройках. Раньше оно выбирало первый свободный порт».
- Используйте названия, которые видит читатель. Команды, параметры, коды ошибок, имена API,
  файлы и сообщения выделяйте как код. Сохраняйте точное написание. Внутренние имена классов,
  модулей, функций и веток, а также служебные номера задач оставляйте в истории разработки.
- Для исправления опишите симптом. Если внутренняя причина помогает определить затронутую
  платформу, объём данных или режим работы, укажите её вторым предложением.
- Для изменения производительности приведите условия и результат. Например, импорт миллиона
  записей раньше занимал 41 с, а после обновления занимает 13 с.
- Исключите общие оценки вроде «мелкие исправления», «оптимизировано» и «повышена стабильность».
  Уберите сведения об исполнителе и ходе работы. По записи читатель должен понять, что изменилось в продукте.
- Если задача, запрос на слияние, бюллетень или пункт спецификации помогает читателю, дайте ссылку
  в самой записи. Убедитесь, что читатель может её открыть. Номер задачи без ссылки и путь
  к закрытому документу для этого не подходят.
- Подробное объяснение вынесите по ссылке. Если изменение видно на экране, можно добавить один
  снимок экрана или короткую видеозапись.

**Примеры записей на английском**

```markdown
- `build --watch` no longer hangs when stdin is closed (#1234).
- Export to PDF now keeps vector diagrams; the file stays editable in the editor.
- Parser: recover from a missing final chunk instead of raising (#1250).
- Rewrote the JSON parser; importing 1 000 000 records takes 13 s instead of 41 s.
```

**Примеры записей, которые нужно доработать**

```markdown
- Misc improvements and bug fixes.
- Refactored `ExportService`, upgraded `pdfgen` to 4.2.
- Fixed bug 1234.
- Significantly faster JSON parsing.
- Closed rows 1986–1990 of the internal defect registry.
```

## 8. Ломающие изменения и устаревание

Если обновление нарушает публичный контракт, начните запись с `**Breaking:**`. Поместите такие
записи в начало соответствующей категории. Обычно это `Changed` или `Removed`.

Укажите, что перестанет работать, кого затронет изменение и как перейти на новую версию.
Короткую инструкцию включите в запись, например «Переименуйте опцию `color` в `theme`».
Если нужна длинная инструкция, дайте ссылку на руководство по миграции. На странице релиза
соберите все шаги перехода в одном разделе `Upgrading` над категориями.

Для несовместимого изменения увеличьте MAJOR. В линии `0.Y.Z` увеличьте MINOR.
Выпуск такого изменения в PATCH запрещён.

1. Когда объявляете об устаревании, добавьте запись `Deprecated`. Назовите замену и версию удаления.
2. Удаляйте возможность только в более позднем релизе. В записи `Removed` укажите замену и версию,
   с которой возможность считалась устаревшей.

Включайте все устаревания, удаления и ломающие изменения, даже если других записей нет.

## 9. Известные ограничения

Если на момент публикации известны ограничения, добавьте `Known issues` в конце раздела версии
после категорий. Для каждого ограничения опишите условие, симптом и обходной путь. Дайте ссылку
на задачу, в которой отслеживают исправление.

В каждой следующей версии повторяйте все действующие ограничения. Так читателю достаточно
открыть описание своей версии. Когда ограничение устранено, удалите его из `Known issues` и добавьте
запись в `Fixed` этого релиза. Если на момент публикации известных ограничений нет, опустите раздел.

## 10. Черновик от инструментов и моделей

Черновик можно подготовить по коммитам с помощью semantic-release, release-please, Changesets
или git-cliff. Можно передать модели изменения в коде (diff). На GitHub генератор собирает
принятые запросы на слияние по меткам из `.github/release.yml`. [Генератор описаний GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)

1. Пишите заголовок запроса на слияние для того, кто обновляется. При слиянии объединяйте коммиты
   в один (squash). Тогда заголовок станет основой коммита и будущей записи.
2. Используйте типы Conventional Commits при подготовке черновика. Для `feat` рассмотрите `Added`
   и увеличение MINOR. Для `fix` рассмотрите `Fixed` и увеличение PATCH. Знак `!` или строка
   `BREAKING CHANGE:` в конце сообщения обозначает несовместимость.
3. Дайте модели и участнику проекта одно задание. Сохраните его в файле инструкций для агентов,
   например `AGENTS.md` или `CLAUDE.md`. Попросите отобрать изменения, заметные пользователю,
   и объяснить причину каждого. Требуйте одну категорию на запись и пометку для каждого несовместимого
   изменения. Опустите служебные изменения и перечень коммитов.
4. Сверьте черновик со всеми изменениями между предыдущим и новым тегами. Для каждого принятого
   изменения проверьте, есть ли запись или основание пропустить её по §1 и §6.
5. Прежде чем показывать черновик другим, поручите редактору проверить его по §14. Один результат
   может объединять несколько коммитов. Редактор отвечает за отбор и описание результата.

Системе непрерывной интеграции (CI) поручите перенос `Unreleased` в датированный раздел,
проверку формата и напоминание о записи. Разрешите слияние без изменения журнала, если
пользователю нечего сообщить. Обязательная правка файла при каждом слиянии создаёт пустые по смыслу записи.

## 11. Страница релиза и файлы

1. Создайте аннотированный тег на коммите релиза и отправьте тег на хостинг (§3).
2. Создайте черновик релиза для этого тега. Скопируйте текст версии из журнала. При несовместимых
   изменениях добавьте `Upgrading`. Подготовьте раздел `Artifacts` и ссылку на сравнение тегов.
3. Прикрепите по одному файлу для каждой поддерживаемой платформы. Используйте имя
   `<продукт>-<версия>-<ОС>-<архитектура>.<формат>`. Для открытого продукта приложите исходный код.
   Если пользователи проверяют подпись, приложите её.
4. Рассчитайте контрольные суммы по загруженным файлам. Приложите `SHA256SUMS` для всех архивов
   и проверьте суммы. Укажите на странице команду проверки для пользователя `sha256sum -c SHA256SUMS`.
5. В `Artifacts` укажите коммит тега, рабочий процесс сборки и его конкретный запуск. Перечислите
   выполненные проверки и их результаты. Для чисел укажите условия замера (§7).
6. Проверьте флаги `prerelease` и `Latest` (§3) и опубликуйте готовый релиз. Если релиз
   исправляет уязвимость, одновременно опубликуйте бюллетень безопасности (security advisory).

Подписчики видят релиз сразу после публикации. Если на GitHub включён режим неизменяемых релизов,
хостинг защищает опубликованные тег и файлы от изменения и удаления. [Документация GitHub о релизах](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

**Пример для GitHub CLI.** В шаблоне команды замените название продукта и `<файлы>` своими значениями.

```sh
gh release create v2.3.0 --draft --verify-tag --title "<Продукт> 2.3.0" --notes-file release.md <файлы>
```

Флаг `--draft` оставляет релиз в черновиках до проверки. Всегда указывайте `--verify-tag`.
Если тега ещё нет на хостинге, команда с этим флагом завершится с ошибкой. Без флага `gh`
может создать тег на вершине ветки по умолчанию. Для линии `0.Y.Z` и кандидатов добавьте
`--prerelease`. [Справка по gh release create](https://cli.github.com/manual/gh_release_create)

В конце страницы укажите ссылку `Full changelog` на сравнение предыдущего и нового тегов.
Формат ссылки — `<хостинг>/<владелец>/<репозиторий>/compare/<старый>...<новый>`.

## 12. Отозванная и исправленная версия

**Дефект в опубликованном файле.** Выпустите исправленный файл под новым номером версии.
По п. 3 SemVer содержимое выпущенной версии должно оставаться неизменным.

**Отзыв версии.** Если вы отзываете версию из-за серьёзного дефекта или уязвимости, сохраните
её в журнале. Добавьте пометку `[YANKED]` к заголовку версии, например `## [2.3.0] - 2026-11-24 [YANKED]`.
Добавьте ту же пометку в заголовок страницы релиза. В начале описания укажите причину отзыва
и версию для перехода. Сохраните исходный тег на месте. Так пользователь сможет найти описание
установленной версии, а инструменты по тегу получат прежний коммит.

**Пропуск в описании.** Если после публикации обнаружилась пропущенная запись, добавьте её.
Рядом укажите дату правки.

## 13. Отклонения

Если продукт отступает от правила, внесите отклонение в таблицу раздела «Отклонения от конвенции
по описанию релизов» в документации продукта. Укажите правило, принятое решение, причину, цену
и условие снятия отклонения. Объясните причину применительно к продукту. Формулировки «у нас так
принято» недостаточно. При ревью верните описание на доработку, если обнаружите незаписанное отклонение.

**Примеры отклонений**

- Небольшой продукт использует один хостинг. Команда ведёт журнал на страницах релизов
  и помещает ссылку на них в `CHANGELOG.md`. При переносе кода журнал останется на прежнем хостинге.
- Продукт выходит по расписанию. Команда использует календарную нумерацию, например `2026.11.1`,
  и указывает схему в начале журнала.
- Команда поставляет продукт непрерывно, без номеров версий. Она помещает датированные записи в `Unreleased`.
- Команда вводит седьмую категорию. Она обосновывает, для каких изменений недостаточно шести категорий.

## 14. Чек-лист перед публикацией

```markdown
- [ ] Номер версии соответствует самому сильному изменению по таблице §2.
- [ ] Номер совпадает в теге, заголовке релиза, разделе журнала, именах файлов и самом продукте.
- [ ] Аннотированный тег v<X.Y.Z> или <продукт>-v<X.Y.Z> стоит на исходном коммите релиза.
- [ ] Для линии 0.Y.Z и кандидатов установлен prerelease. Только последний стабильный релиз отмечен Latest.
- [ ] Заголовок содержит название продукта и версию. Канал указан в скобках. Текст начинается с описания.
- [ ] Под пустым Unreleased стоит новая версия с заголовком вида ## [2.3.0] - 2026-11-24.
- [ ] Номер версии ведёт на сравнение с предыдущим тегом. Для первой версии ссылка ведёт на тег.
- [ ] Записи распределены по шести категориям в порядке §5. Пустые категории опущены. Области указаны внутри категорий.
- [ ] Несовместимые изменения стоят в начале своих категорий. Каждая такая запись начинается с **Breaking:**.
- [ ] Если обновление нарушает совместимость, на странице есть шаги перехода в Upgrading.
- [ ] В Deprecated указаны замена и версия удаления. Удаление выпущено позже объявления об устаревании.
- [ ] Каждая запись Security начинается с идентификатора, называет затронутые версии и ведёт на бюллетень. Бюллетень выходит вместе с релизом.
- [ ] Каждая запись называет конкретное изменение и его последствия для пользователя. Для чисел указаны условия замера.
- [ ] Пользователь узнаёт названия и может открыть ссылки. Общие оценки и внутренние подробности исключены.
- [ ] В Known issues перечислены все действующие ограничения. Для каждого указаны условие, симптом, обходной путь и ссылка.
- [ ] Редактор сверил записи с диапазоном между тегами. Для каждого пропуска есть основание по §1 и §6.
- [ ] Если черновик подготовил инструмент или модель, человек проверил его по этому списку.
- [ ] Приложены файлы для каждой поддерживаемой платформы. Проверка SHA256SUMS прошла для всех архивов.
- [ ] Черновик привязан к существующему тегу. Флаги проверены перед публикацией.
- [ ] Каждое отклонение записано в таблице продукта с причиной, ценой и условием снятия.
```

## Приложение. Пример

**Фрагмент журнала `CHANGELOG.md`**

```markdown
# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
The version covers the command line, exit codes and the project file format.

## [Unreleased]

## [2.4.0] - 2026-11-24

Synchronization of large projects is faster; `--legacy-sync` is deprecated.

### Changed

- Synchronizing a project of 10 000 files takes 8 s instead of 25 s.

### Deprecated

- The `--legacy-sync` flag. Use `--sync-mode=fast` instead; the flag is removed in 3.0.0.

### Fixed

- Export to PDF no longer drops diagrams when the project was opened from a network share ([#889](https://github.com/example/product/pull/889)).

[Unreleased]: https://github.com/example/product/compare/v2.4.0...HEAD
[2.4.0]: https://github.com/example/product/compare/v2.3.0...v2.4.0
[2.3.0]: https://github.com/example/product/compare/v2.2.1...v2.3.0
```
