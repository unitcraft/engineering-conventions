# Конвенция по HTTP API

**Редакция 1.2, 2026-11-28.** Применяйте конвенцию к внутренним сервисам, публичным API и локальным
приложениям с веб-интерфейсом. При проектировании операции определите запрос, успешный ответ,
ошибки и поведение при повторе. Форматы значений и правила хранения приведены в [конвенции по БД](database.md).

Проверяйте контракт линтером, поведение сервиса — тестами, а причины отклонений — на ревью (§19).

## 0. Принципы

- Выбирайте HTTP-метод по назначению операции. Код состояния сообщает исход, заголовки передают
  метаданные, тело содержит данные. Собственный протокол поверх `POST` требует обоснования,
  почему задачу нельзя решить более узким правилом.
- Исключите из URL персональные данные (ПДн) и идентификаторы людей. Адрес попадает в журналы,
  историю браузера, закладки, снимки экрана и `Referer` (§2.3).
- Используйте общие формы ошибок и страниц коллекций. Во всём API применяйте единые имена
  идентификаторов и форматы времени.
- Сервис сам проверяет запрос и права. Проверка в клиенте служит для обратной связи пользователю.
- Если запрос нарушает контракт, верните ошибку. Это касается лишнего поля, неизвестного
  параметра, превышения лимита и неверного ключа идемпотентности.
- Включайте диагностические заголовки в успешные ответы и ошибки. В ошибке указывайте `request_id`.
- Возвращайте только сведения, необходимые клиенту. Защитите чужие данные и сведения о существовании
  закрытых объектов. Исключите версии ПО, имена хостов, стеки вызовов и SQL.

## 1. Транспорт

### 1.1. TLS

Используйте TLS 1.2 или новее для всех сетевых соединений. Предпочтительна версия 1.3.
Правило действует между сервисами, для клиентов, служебных маршрутов, проб оркестратора
и среды разработки. Внутренний узел может быть скомпрометирован. Одинаковые настройки
в разработке и эксплуатации позволяют заранее проверить защищённые Web API и HSTS.

Не открывайте порт для обычного HTTP, в том числе для перенаправления с порта `80`.
До перенаправления клиент уже передаст заголовок `Authorization` и тело без шифрования.
Исключение допускается для процесса, доступного исключительно через loopback (`127.0.0.1`, `::1`).
При привязке к сетевому интерфейсу используйте TLS.

В ответах браузеру сам сервис должен установить `Strict-Transport-Security` со сроком не менее года
и остальные заголовки по §14.3. Периметр может дублировать эти заголовки.

### 1.2. Учётные данные

Для каждого маршрута объявите один источник учётных данных. По умолчанию используйте только
`Authorization` со схемой `Bearer <token>` или другой объявленной схемой. На таком маршруте не читайте,
не записывайте в лог и не пересылайте `Cookie`. Исключите токен из пути и строки запроса (§2.3).

Если браузерный клиент не может установить заголовок, допускается cookie-сессия. Примеры —
страница того же сервера, `EventSource` и скачивание файла по ссылке. Для такого маршрута:

1. Принимайте учётные данные в теле `POST` и устанавливайте cookie ответом. Вход по ссылке с токеном запрещён.
2. Установите `HttpOnly`, `SameSite=Strict`, ограниченный `Path` и срок жизни. Установите `Secure`,
   кроме случая loopback.
3. Проверяйте `Origin` на каждой изменяющей операции (§14.2).

Проверяйте токен в сервисе, даже если шлюз уже выполнил проверку. При смене или отзыве токена
немедленно закройте все сессии, выданные по нему.

### 1.3. Ограничения на входе

До разбора тела и аутентификации общая обвязка (§16) применяет следующие ограничения.

| Условие | Действие |
|---|---|
| Тело превышает предел | Верните `413`. Проверяйте `Content-Length` и фактический объём при чтении. |
| Один заголовок или все заголовки вместе превышают предел | Верните `400`. |
| Повторяется `Host` или `Content-Length` либо в заголовке есть управляющий символ | Отклоните запрос с `400`. Выбор одного значения оставляет запрос неоднозначным. |
| Тип тела `Content-Type` отсутствует в контракте | Верните `415`. |
| Клиент медленно передаёт запрос или открывает много соединений | Ограничьте время чтения заголовков и тела, а также число соединений с одного адреса. |

## 2. Адресация

### 2.1. Схема пути

```
/api/v<major>/<resource>[/<id>[/<sub_resource>[/<id>]]]
/api/v<major>/<resource>/<id>/<action>          # доменное действие
/api/v<major>/<resource>/search                 # чтение с фильтрами, которым нельзя в URL
```

- Для коллекций используйте множественное число и латиницу в `snake_case`, например `work_orders`
  или `issue_positions`. Если экземпляр один (настройки, текущее состояние, сессия вызывающего),
  используйте единственное число без `{id}`: `/api/v1/settings`, `/api/v1/session`.
  Для действия над таким ресурсом добавьте глагол, например `POST /api/v1/settings/reset`.
- Ограничьте вложенность пути двумя ресурсами. Для более глубокой вложенности выделите ресурс
  с собственным адресом.
- Если операция выражает доменное действие, например `complete`, `cancel`, `approve` или `recalculate`,
  используйте отдельный `POST` с глаголом в пути. Задайте схему тела, права и запись в журнале
  для этого действия. Специальный флаг в `PATCH` для такого перехода запрещён.
- Включайте `v<major>` в путь. Выпустите новую основную версию, если удаляете или переименовываете
  поле, меняете его тип или смысл кода ошибки. Это же правило действует, если новая валидация
  отклоняет ранее допустимый запрос. Добавление необязательного поля, кода в объявленный список
  или нового ресурса совместимо с прежней версией.
- Если продукт сам развёртывает всех потребителей и клиент с сервером составляют один артефакт,
  версию можно передавать в заголовке и служебном ответе. Оформите отклонение по §19.

### 2.2. Методы

| метод | семантика | тело запроса | идемпотентен |
|---|---|---|---|
| `GET` | чтение, без побочных эффектов; параметры только в query (§2.3) | нет (тело у `GET` теряется по дороге) | да |
| `POST` | создание, доменное действие, поиск с параметрами, которым нельзя в URL | JSON | нет, кроме объявленной идемпотентности (§10) |
| `PUT` | полная замена ресурса | JSON, весь ресурс | да |
| `PATCH` | частичное изменение, JSON Merge Patch (RFC 7386) | JSON | да при `If-Match` |
| `DELETE` | удаление | нет | да |

Обрабатывайте `HEAD` и `OPTIONS` в общей обвязке. Если путь существует, но метод для него
не предусмотрен, верните `405` с `Allow`. На ревью отклоняйте `GET` с побочным эффектом
и `POST` для чтения без основания из §2.3.

### 2.3. Что запрещено в URL

Проверяйте и сегменты пути, и параметры строки запроса (query). Исключите из них следующие данные:

- ПДн из реестра продукта, включая почту, телефон, ФИО, документы, адреса, логины, номера договоров
  и лицевых счетов (§13.7 конвенции по БД).
- Идентификаторы субъектов, например `person_id`, `employee_id`, `customer_id` и `user_id`.
  Для собственных данных используйте контекст токена (`/api/v1/me/...`). Для разрешённого чтения
  чужих данных используйте тело `POST .../search` или ссылку из полученного ресурса с нейтральным идентификатором.
- Учётные данные и секреты, включая токены, ключи API, одноразовые коды и подписи для доступа по ссылке.
- Значимые естественные ключи, например `ЗАЯВ-000123`, ИНН или табельный номер.

Адресуйте объекты по непрозрачному UUID v7. URL может содержать идентификатор документа, заказа
или устройства, курсор, лимит, порядок сортировки и фильтры по перечислениям, датам и объектам.
Тогда возможны кэширование и условные запросы, но в журнале останется факт обращения к объекту.
Если сам факт обращения чувствителен, перенесите чтение на `POST .../search` и обоснуйте отклонение (§19).

Проверяйте контракт по списку запрещённых имён (`email`, `phone`, `inn`, `passport`, `*_name`,
`person_id`, `user_id`, `token`, `key` и другие). Линтер должен завершать сборку с ошибкой,
если такое имя указано с `in: path` или `in: query`. Тест маршрутов должен принимать
только переменные сегменты `{id}` формата UUID.

### 2.4. Фильтры, которым нельзя в URL

Для фильтра по ПДн или идентификатору субъекта используйте `POST /<resource>/search`.
Передайте в теле параметры коллекции `cursor`, `limit`, `sort`, `filter`, `expand` (§4.1).
Верните ту же форму страницы, что у `GET`.

Объявите `search` операцией чтения. Клиент может повторить её без ключа идемпотентности.
Продлевайте сессию только по пометке (§8.4). Кэширование допускается только в памяти процесса
и только для ответа без ПДн.

### 2.5. Query-параметры

- Для каждой операции перечислите допустимые параметры. При неизвестном имени верните
  `400 invalid_parameter`. Пропущенный фильтр может привести к выдаче всей выборки.
- Если параметр объявлен массивом, его можно повторить, например `status=a&status=b`.
  Для остальных повторов верните `400`.
- Кодируйте значения по RFC 3986. Для дат и моментов используйте §11.

## 3. Тело запроса и ответа

- Используйте JSON в UTF-8. Для запроса с телом и успешного JSON-ответа укажите
  `Content-Type: application/json; charset=utf-8`. Для ошибки укажите `application/problem+json; charset=utf-8`.
- Называйте ключи латиницей в `snake_case`. Используйте одно имя в JSON, модели и колонке БД.
  Первичный идентификатор ресурса назовите `id`. Имена `<entity>_id` используйте для ссылок.
- Передавайте на верхнем уровне объект. Например, пакетная операция принимает `{ "items": [...] }`.
  К объекту можно добавить необязательное поле без изменения его формы. Если операция принимает
  тело, но параметров пока нет, передавайте `{}`.
- Возвращайте сам ресурс. Не добавляйте обёртки `data`, `result` или `success`. Исход операции
  передаёт код состояния, диагностику — заголовки, метаданные коллекции — объект страницы.
- Включайте каждое объявленное поле. При отсутствии скалярного значения передайте явный `null`.
  Для именованного поля-массива передавайте массив, в том числе пустой `[]`.
- Ограничьте вложенность тремя уровнями. Корень занимает первый уровень, индекс массива
  уровень не добавляет. Для более глубокого объекта выделите самостоятельный ресурс.
- Передавайте связанную сущность ссылкой, например `counterparty_id`. Встраивайте её только
  по `expand`. Задайте закрытый список связей. При неизвестном значении верните `422`.
- Неограниченную коллекцию выдавайте отдельным подресурсом с пагинацией. Встроенная коллекция
  допустима, когда её размер ограничен по смыслу и указан в контракте.

## 4. Коллекции

### 4.1. Запрос

Пример запроса коллекции:

`GET /api/v1/issues?cursor=…&limit=50&sort=-created_at&status=draft,in_progress&expand=counterparty`

| параметр | обязательность | смысл |
|---|---|---|
| `cursor` | нет | непрозрачный курсор предыдущей страницы; отсутствие или пусто: первая страница |
| `limit` | нет | размер страницы; умолчание и максимум зафиксированы в контракте операции; превышение `400`, не обрезание |
| `sort` | нет | список полей с префиксом `-` для убывания; допустимые поля перечислены в контракте |
| фильтры | нет | по одному параметру на поле, закрытый список, значения из перечислений и форматов §11 |
| `expand` | нет | закрытый список связей |

В контракте продукта задайте классы операций и предел `limit` для каждого класса.
Примеры значений (максимум и значение по умолчанию): обычные списки — 200 и 50, справочники —
500 и 100, списки с ПДн — 100 и 25. Если ответ содержит хотя бы одно поле с ПДн, примените
пониженный предел. Он дополняет суточную квоту на выдачу ПДн.

### 4.2. Ответ

```json
{
  "items": [ { "id": "01903f2a-…", "status": "draft" } ],
  "next_cursor": "eyJpZCI6…",
  "has_more": true
}
```

Всегда возвращайте массив `items` и поле `next_cursor`. Для последней страницы установите
`next_cursor` в `null`. Поле `has_more` сообщает интерфейсу, есть ли следующая страница.

Используйте непрозрачный курсор. Клиент передаёт курсор без разбора. Если сервер не может
декодировать курсор, верните `400`. Пагинация по `OFFSET` требует пропускать прочитанные строки,
а при параллельных вставках состав страниц меняется.

Исключите `total` из страницы. Если нужен счётчик, создайте `GET /<resource>/count` с теми же фильтрами.
Пометьте операцию в контракте как дорогую. Для приблизительного значения верните `approximate: true`.

Ограничивайте выборку правами вызывающего независимо от фильтров. Если ему недоступны все объекты
выборки, верните `200` с пустым `items`. Такой же ответ дайте при фильтре по идентификатору
чужого объекта. Применяйте ту же область видимости к `count` (§7.3).

## 5. Валидация

Проверяйте запрос на сервере, даже если клиент уже выполнил проверку. Запрос может поступить
из старой версии, очереди, интеграции или `curl`.

1. Проверьте транспорт и заголовки (§1.3).
2. Проверьте учётные данные и права.
3. Проверьте тело по закрытой схеме. Для каждого поля проверьте тип, формат, диапазон, длину,
   принадлежность перечислению и зависимости полей (например, `date_to >= date_from`).
   У каждой строки должен быть максимум длины. Примеры форматов — UUID v7, момент ISO 8601 с `Z`
   и десятичная строка.
4. Только после успешной проверки схемы применяйте бизнес-правила. К работе с данными переходите
   после проверок. Значение, нарушающее схему, не должно попасть в бизнес-логику или запрос к БД.

Если запрос нельзя разобрать или нарушены правила обращения, верните `400`. Примеры — повреждённый
JSON или курсор, превышение `limit`, неверный формат обязательного заголовка. Для неизвестного
параметра query верните `400 invalid_parameter`. Клиент показывает общую ошибку.

Если разобранное тело нарушает схему или бизнес-правило, верните `422`. Для лишнего поля
используйте `422 extra_forbidden`. Соберите все найденные нарушения в `errors[]` одного ответа.
Клиент подсвечивает соответствующие поля. В сообщении исключите полное присланное значение,
регулярные выражения схемы, имена таблиц и классов, сведения о других значениях в системе.

После сохранения пользовательское значение по-прежнему требует обработки в контексте вывода.
Экранируйте HTML, обрабатывайте имена файлов и управляющие символы в логах. Передавайте значения
в SQL параметрами. Не используйте присланное значение как путь, заголовок, ключ хранилища или часть `type` ошибки.

## 6. Ошибки

Все сервисы продукта возвращают ошибки в формате Problem Details (RFC 9457, преемник RFC 7807).
Укажите `Content-Type: application/problem+json; charset=utf-8`.

```json
{
  "type": "urn:<product>:problem:validation-error",
  "title": "Ошибка валидации",
  "status": 422,
  "detail": "Проверьте заполнение полей",
  "instance": "/api/v1/issues",
  "code": "validation_error",
  "request_id": "01903f2a-7c1e-7a3b-9f21-6d4e2b8c9a10",
  "errors": [
    { "field": "positions[0].quantity", "code": "greater_than", "message": "Должно быть больше 0" }
  ]
}
```

| поле | когда | смысл |
|---|---|---|
| `type` | всегда | URN `urn:<product>:problem:<code-с-дефисами>`; URN, а не URL, чтобы не публиковать страницы и не раскрывать внутренние домены |
| `title` | всегда | короткий заголовок для человека на языке продукта |
| `status` | всегда | тот же код состояния, что в строке ответа |
| `detail` | всегда | развёрнутый текст для человека, без технических подробностей |
| `instance` | всегда | **шаблон** пути операции (`/api/v1/issues/{id}`), не конкретный URL: конкретный путь мог бы содержать идентификатор, а тело ошибки показывается пользователю и уходит в поддержку |
| `code` | всегда | машинный код `snake_case` из закрытого каталога продукта; клиент ветвится только по нему |
| `request_id` | всегда | UUID v7 запроса, тот же, что в заголовке `X-Request-Id` |
| `errors[]` | только валидация | `field` полный путь до поля (`positions[0].quantity`, `filter.status`), `code` машинный, `message` человеческий |

Ведите каталог `code` вместе с контрактом. Обвязка механически преобразует `code` в `type`.
Определяйте код в каталоге до использования в обработчике. Клиент выбирает действие по `code`.
Поля `title` и `detail` предназначены для читателя и могут меняться при редактуре.

Включайте `errors[]` только для ошибок валидации. Остальные поля обязательны для каждой ошибки.
При необработанном исключении обвязка возвращает `500` с общим текстом и `request_id`.
Исключите пустой ответ и HTML-страницу фреймворка.

Не включайте в тело ошибки стек вызовов, фрагменты кода, SQL, имена таблиц, сообщения драйверов,
имена хостов, порты, версии ПО, дампы запроса, ПДн, токены или подписи. Для внутренней диагностики
свяжите разрешённые сведения с `request_id` в журнале с учётом ограничений §14.5 и §15.

## 7. Коды состояния

### 7.1. Успех

| код | когда | обязательно |
|---|---|---|
| `200` | чтение или изменение с телом | тело ресурса или страницы |
| `201` | создано | тело созданного ресурса с `id`; заголовок `Location` с его адресом |
| `202` | запущена фоновая задача | тело `{ "id", "state", "status_url" }` задачи и `Location` на ресурс задачи; `state` из `queued \| running \| succeeded \| failed \| cancelled` |
| `204` | успех без тела (`DELETE`, действие без результата) | тела нет; диагностические заголовки есть |
| `304` | условный `GET`, ресурс не менялся | тела нет; `ETag` |

Возвращайте `2xx` только при успехе. Ответ `200` с телом `{ "success": false }` скрывает ошибку
от мониторинга и мешает клиенту применить политику повторов.

### 7.2. Ошибки клиента

Выберите код по причине отказа. Возвращайте указанные в таблице обязательные заголовки даже при пустом теле ответа.

| код | когда |
|---|---|
| `400` | битый JSON, битый курсор, неизвестный или неверный параметр query, `limit` сверх максимума, отсутствующее или не-JSON тело там, где оно нужно, неверный формат обязательного заголовка (`Idempotency-Key` не UUID v7), нарушения §1.3 |
| `401` | нет учётных данных, токен невалиден или просрочен, сессия закрыта; различаются `code` (§8.1) |
| `403` | учётные данные валидны, но нет права на класс операции (scope). Не на конкретный объект (§7.3) |
| `404` | ресурса нет **или** вызывающий не вправе его видеть |
| `405` | путь существует, метод к нему не применим; `Allow` обязателен |
| `409` | конфликт состояния: уникальность, недопустимый переход, повторный `Idempotency-Key` при другом теле (`conflict`), повтор при идущей обработке (`idempotency_in_progress` + `Retry-After`) |
| `410` | ресурс удалён окончательно |
| `412` | условие `If-Match`/`If-Unmodified-Since` не выполнено: ресурс изменён с момента чтения |
| `413` | тело или файл больше предела |
| `415` | `Content-Type` не из контракта |
| `422` | нарушена схема или бизнес-правило; лишнее поле |
| `428` | операция требует `If-Match`, а его нет |
| `429` | превышен лимит частоты; `Retry-After` обязателен |

### 7.3. `404`, а не `403`, на чужой объект

Если вызывающий не может видеть конкретный объект, верните `404`. Этот же код получает запрос
несуществующего объекта. Так по ответу нельзя определить, существует ли объект и кому он принадлежит.
Если у вызывающего нет права на класс операций (scope), верните `403`. Для коллекций применяйте §4.2.

### 7.4. Ошибки сервера

| код | когда |
|---|---|
| `500` | неперехваченная ошибка; клиенту нейтральный текст и `request_id` |
| `502` | апстрим вернул невалидный ответ; `Retry-After`, если срок известен |
| `503` | сервис или зависимость недоступны, перегрузка, старт; **`Retry-After` обязателен** |
| `504` | таймаут зависимости; `Retry-After`, если срок известен |

Используйте стандартный HTTP-статус. Для уточнения причины передайте поле `code`.
Коды `440`, `419` и `499` запрещены: прокси, библиотеки и мониторинг могут их не распознать.

## 8. Аутентификация, сессия, права

### 8.1. Коды отказа

| ситуация | статус | `code` | что делает клиент |
|---|---|---|---|
| токен просрочен, сессия жива | `401` | `token_expired` | молча обновляет токен и повторяет один раз |
| сессия закрыта (бездействие или предельный срок) | `401` | `session_expired` | показывает объяснение, ведёт на вход; токен не обновляет |
| учётных данных нет либо токен не прошёл проверку (подпись, издатель, отзыв) | `401` | `unauthenticated` | ведёт на вход |
| прав на класс операции нет | `403` | `forbidden` | показывает «нет прав»; вход не предлагает, сессию сохраняет |

При истечении срока по бездействию и при достижении предельного срока возвращайте один код
`session_expired`. Исключите из тела `login_url`, время истечения, оставшееся время и идентификатор сессии.

Устанавливайте `WWW-Authenticate` только для схемы `Bearer` по RFC 6750 и только если клиенту
не нужен собственный браузерный сценарий входа. Иначе браузер может открыть лишнее окно ввода
учётных данных. Показывайте форму входа только в ситуациях из таблицы.

### 8.2. Сессия по бездействию (если у продукта она есть)

Если у продукта есть таймаут бездействия, сервер ведёт время последнего действия. Заявления
клиента об активности недостаточно для продления сессии.

| Операция | Когда сервер продлевает сессию |
|---|---|
| Изменяющая | Всегда. |
| Чтение, для которого в контракте указано `on_marker` | Только при `X-<Product>-User-Action: true`. |
| Прочие чтения и фоновая активность | Никогда. |

Ставьте пометку централизованно в API-клиенте по источнику вызова. Фоновые опросы, обновление
токена, кадры потока, служебные запросы, повторная отправка очереди и обновление при возврате
фокуса не должны поддерживать сессию. Иначе работающий в фоне интерфейс может сохранять её бессрочно.

Клиент отсчитывает оставшееся время от своей последней помеченной операции. Не вводите отдельный
запрос состояния сессии. При `session_expired` клиент сразу принимает решение сервера.
Сохраните локальные черновики и очереди при истечении сессии.

### 8.3. Права

Проверяйте права в сервисе, даже если перед ним стоит шлюз. Проверяйте доступ к объекту
при каждом чтении и изменении, включая повтор по ключу идемпотентности. При поиске сохранённого
ответа учитывайте субъекта (§10).

### 8.4. Чтение и продление

Классифицируйте `GET`, `search` и `count` как чтение. Клиент может повторять их без ключа
идемпотентности. Для продления сессии применяйте условия §8.2.

## 9. Заголовки ответа и кэширование

### 9.1. Обязательные заголовки каждого ответа

Применяйте правила таблицы к каждому ответу, включая `204`, ошибки и файлы. Для `Retry-After`
учитывайте указанные коды состояния.

| заголовок | что несёт |
|---|---|
| `X-Request-Id` | UUID v7 запроса |
| `Cache-Control` | явная политика (§9.3) |
| `Retry-After` | при `429` и `503` всегда; при `502`/`504`, если срок известен |

### 9.2. Обязательные, когда сервисов или экземпляров больше одного

Если продукт использует несколько сервисов или экземпляров, включите следующие заголовки.

| заголовок | что несёт |
|---|---|
| `traceparent` | W3C Trace Context, продолжается сквозь все вызовы |
| `X-<Product>-Module` | имя сервиса из конфигурации |
| `X-<Product>-Instance` | **непрозрачный** идентификатор экземпляра (UUID v7 при старте), без hostname, адреса и имени контейнера |
| `X-Processing-Time-Ms` | время обработки внутри обвязки, мс |

Рекомендуются `Server-Timing`, `X-Request-Received-At` и `X-Response-Sent-At`. Для моментов
используйте ISO 8601 в UTC с миллисекундами. Если у продукта один процесс без распределённой
трассировки, оформите отсутствие набора одной строкой по §19.

Помещайте диагностику в заголовки. Тогда клиент получит её и с ответом `204`, и с бинарным файлом.

### 9.3. Кэш и условные запросы

- Для `GET` ресурса вычисляйте сильный `ETag` по версии или хэшу представления.
  При совпадении `If-None-Match` возвращайте `304`.
- Укажите `Cache-Control` в каждом ответе. Для персонализированного ответа и ответа с ПДн
  используйте `private, no-store`. Для публичного справочника используйте `public, max-age=<с>, must-revalidate`.
  Задавайте политику явно и для запросов под `Authorization`. Промежуточные кэши не должны сохранять эти ответы.
- Ответ с ПДн разрешено кратковременно кэшировать только внутри процесса. Исключите внешние копии
  в Redis, на диске и на шлюзе.

### 9.4. Оптимистическая блокировка

Если контракт объявляет ресурс версионируемым, требуйте `If-Match: <etag>` для `PUT`, `PATCH`,
`DELETE` и доменных действий. Если заголовок отсутствует, верните `428 precondition_required`.
Если версия не совпала, верните `412 precondition_failed` с актуальным представлением в теле.
Клиент сможет показать изменения и избежать перезаписи данных из другой вкладки (§10.3).

### 9.5. Заголовки, которых в ответе нет

Удалите `Server`, `X-Powered-By`, `Via`, заголовки шлюза и другие заголовки, раскрывающие
фреймворк, версию, хост или имя контейнера. Проверьте ответ на стороне клиента. Прокси может
добавить заголовки после обработки запроса приложением.

## 10. Идемпотентность

### 10.1. Что идемпотентно само

Идемпотентны `GET`, `HEAD`, `PUT`, `DELETE`, `search` и `count`. После успешного `PUT`
повтор со старым `If-Match` получает `412`. После удаления повторный `DELETE` получает `404`
или `410`. Используйте проверку версии, если при `412` клиент может перечитать ресурс и определить
результат своей операции.

### 10.2. Когда нужен `Idempotency-Key`

Объявите обязательный ключ для изменяющего `POST`, который клиент может отправить снова
после потери ответа. Примеры — создание из офлайн-очереди, доменное действие из интеграции,
автоматическая повторная отправка шлюзом. Решение задаёт контракт конкретной операции.

| ситуация | ответ |
|---|---|
| операция объявила ключ, он не передан | `400 invalid_parameter`, операция не выполняется |
| ключ не UUID v7 | `400 invalid_parameter` |
| ключ предъявлен операции, которая его не объявляла | `400 invalid_parameter`: молча выбросить значит отказаться от гарантии, не сказав клиенту |
| ключ встречается первый раз | штатная обработка; успешный ответ запоминается под этим ключом |
| повтор ключа с тем же телом | отдаётся запомненный ответ, добавляется `X-Idempotent-Replay: true` |
| повтор ключа с другим телом | `409 conflict` |
| повтор ключа, пока первый запрос не завершён | `409 idempotency_in_progress` + `Retry-After` |

- Ищите ответ по паре «субъект и ключ». Для другого субъекта тот же ключ считается новым.
  При выдаче сохранённого ответа основной обработчик не выполняется. Учитывайте права по §8.3.
- Сравнивайте хэш пути операции и исходных байтов тела. Не нормализуйте JSON. Клиентская очередь
  должна повторять сохранённый запрос. Храните только отпечаток запроса, поскольку тело может содержать ПДн.
- Сохраняйте только ответы `2xx`. При ошибке освободите ключ, чтобы исправленный запрос можно было выполнить.
- Выберите окно хранения с запасом сверх максимального срока жизни элемента клиентской очереди.
  Для клиентов без очередей достаточно 72 часов.
- Клиент создаёт ключ при постановке операции в очередь. Он хранит ключ вместе с операцией и использует
  его при каждой отправке.
- Реализуйте механизм один раз в общей обвязке продукта. Отдельные таблицы по модулям запрещены.
  Схема хранения описана в §11.2 конвенции по БД.

### 10.3. Идемпотентность через версию вместо ключа

Операция может объявить в контракте идемпотентность через `If-Match`. Примеры — полная замена
состояния и выпуск секрета с немедленной сменой версии ресурса. Тогда ключ не требуется.
При `412` клиент обязан перечитать ресурс. После обрыва связи без чтения нельзя определить,
применилось ли своё изменение или ресурс изменил другой клиент. Для очереди с накоплением операций
требуется ключ идемпотентности.

## 11. Форматы значений

Используйте форматы из §1, §2, §3.3, §4 и §5 [конвенции по БД](database.md). В таблице приведены
форматы значений в ответе.

| значение | форма | пример |
|---|---|---|
| момент (поля `_at`) | ISO 8601 UTC, строго `Z`, без смещений | `"2026-09-06T18:10:00Z"` |
| календарная дата (поля `_on`) | `YYYY-MM-DD` | `"2026-09-06"` |
| идентификатор | UUID v7 строкой | `"0192a7f0-3c4d-7e21-8a55-0b9c1d2e3f40"` |
| деньги | строка десятичного числа + `currency_code` ISO 4217 | `"amount": "1234.50", "currency_code": "RUB"` |
| количество, доля, процент с дробью | строка десятичного числа | `"quantity": "12.500"` |
| целые счётчики | число JSON | `"count": 42` |
| перечисление | латиница `snake_case` | `"in_progress"` |
| телефон | E.164 | `"+79991234567"` |
| длительность | целые секунды или миллисекунды с суффиксом в имени | `"timeout_sec": 30` |

По умолчанию подписи вроде «2 дня 17 ч» и «вчера» формирует интерфейс с учётом локали.
Если нескольким интерфейсам нужна одна формулировка, можно вернуть подпись в дополнительном
поле с суффиксом `_label` рядом с обязательным машинным значением. Оформите отклонение по §19.

## 12. Потоки и события

- Открывайте Server-Sent Events и WebSocket запросом `GET` по объявленному пути. Применяйте
  общие правила аутентификации. Токен в URL запрещён. Для `EventSource` используйте cookie-сессию по §1.2.
- Включайте в событие монотонный `id`, имя `event` из закрытого списка в `snake_case` и JSON
  в `data` по контракту события.
- При подключении первым событием передавайте текущее состояние (snapshot). Для восстановления
  клиент присылает `Last-Event-ID`. Сервер досылает пропущенные события из буфера. Если буфер
  не покрывает разрыв, первым событием верните полное состояние.
- При отсутствии данных отправляйте `ping` не реже одного раза в 30 с. Кадры потока не продлевают сессию (§8.2).
- Ограничьте число соединений на экземпляр и на субъекта. При превышении верните `503`
  с `Retry-After`. Перед остановкой сервера отправьте финальное событие `bye`.

## 13. Асинхронные операции

При постановке задачи верните `202` с телом `{ "id", "state", "status_url" }` и заголовком
`Location` с адресом задачи. Клиент читает её состояние через `GET /api/v1/tasks/{id}`.
Используйте закрытый список состояний из §7.1. Результат передавайте ссылкой на созданный ресурс.

Постановка задачи меняет состояние. Применяйте правила ключа идемпотентности из §10.
Верните `202` за время, которое продукт отводит на быстрый ответ.

## 14. Безопасность на HTTP-границе

### 14.1. Скрытие деталей

- Исключите версии ПО и сборки из обычных ответов, включая заголовки и `detail`. Клиенту
  доступна версия API в `/api/v<major>`. Для эксплуатации предоставьте номер сборки на внутреннем служебном пути.
- Оставьте проверки работоспособности, метрики и спецификацию работающего сервиса во внутреннем контуре.
  Спецификация раскрывает поля, а метрики — зависимости. Публичный контракт публикуйте из репозитория контрактов.
- Используйте непрозрачный идентификатор экземпляра (§9.2). Исключите абсолютные пути, имена
  пользователей ОС и хостов из всех сетевых ответов, включая служебные поля. Эти сведения
  допустимы только для локального инструмента на loopback.

### 14.2. Доверие входящим заголовкам

1. Проверьте адрес узла, который установил соединение. Если он входит в список доверенных прокси,
   в `X-Forwarded-For` выберите первый справа адрес вне списка.
2. Если узел не входит в список, игнорируйте заголовки с переадресованным адресом. Используйте
   адрес соединения. При пустом списке действует тот же порядок. В таком режиме лимит может
   относиться к адресу прокси, а не отдельного клиента.
3. Передайте одно вычисленное значение в ограничитель частоты, блокировки, аудит и журнал.

Используйте присланные `X-Request-Id`, `Origin` и `User-Agent` для корреляции или проверки.
Не устанавливайте по ним личность. Не подставляйте их в SQL, пути или ключи. Пересылайте
другим сервисам только заголовки из закрытого списка.

На изменяющей операции проверяйте каждый полученный `Origin` по списку разрешённых источников.
Если `Origin` отсутствует, отклоните запрос браузерной сессии. Для межсервисного токена или
ключа агента отсутствие заголовка допустимо.

### 14.3. Заголовки безопасности для браузерных ответов

Установите `Strict-Transport-Security` (§1.1), `X-Content-Type-Options: nosniff` и
`Referrer-Policy: no-referrer`. Последний предотвращает передачу URL с идентификаторами третьим сторонам.
Используйте `Content-Security-Policy`, по возможности без внешних источников. Для защиты
от встраивания используйте `X-Frame-Options: DENY` или `frame-ancestors`. Включайте CORS
только для объявленных источников. Под `Authorization` значение `*` запрещено.

### 14.4. Лимиты

Ограничивайте частоту запросов по вычисленному адресу и по субъекту. Отдельно учитывайте
попытки с неверными учётными данными. Пример порога — десять попыток за минуту с одного адреса
до временного `429`. Сравнивайте секреты за константное время. Задайте суточную квоту на объём выданных ПДн.

### 14.5. Устойчивость к изменению состава ПДн

Используйте единый реестр ПДн (§13.7 конвенции по БД). Из него выводите запреты для URL (§2.3),
класс предела `limit` (§4.1), признак ПДн в ответе, политику кэширования (§9.3) и маскирование
в журналах и экспортах. Тогда новая классификация поля изменит все зависимые проверки.

- Для каждого поля контракта задайте `x-data-class` из списка `none`, `pii`, `subject_id`, `secret`.
  Линтер выводит свойства операции из классов полей. Проверка должна завершаться ошибкой для `pii`
  или `subject_id` в пути, query, имени файла экспорта или событии без соответствующей пометки.
- Заранее относите спорные данные к ПДн. Примеры — сетевой адрес, идентификаторы устройства
  и cookie, геолокация, логин и фотография.
- Исключите ПДн из журналов доступа, неизменяемого аудита, событий брокера с длительным хранением
  и незашифрованных резервных копий. Если аудит должен ссылаться на человека, используйте
  идентификатор записи в изолированной схеме или шифротекст. В последнем случае при удалении уничтожьте ключ.
- Задайте короткий срок хранения журналов. Предусмотрите удаление и маскирование строк по `request_id`
  и по субъекту. Если ПДн попали в журнал, зарегистрируйте инцидент и очистите записи.
- Включите в реестр карту потоков для каждого поля: ответы, экспорты, события, кэши и журналы.
  Назначьте владельца и срок регулярной сверки реестра с действующим законодательством.

## 15. Журналирование

- Обвязка один раз задаёт контекст для каждой строки журнала. Включите `request_id`, `trace_id`
  при наличии, сервис, экземпляр, метод, шаблон пути, субъекта и вычисленный адрес клиента.
- Без согласования со службой информационной безопасности не записывайте тела запросов и ответов
  ни на одном уровне. Нужные для диагностики прикладные идентификаторы обработчик явно добавляет в контекст.
- В журнале доступа сохраняйте URL целиком. По §2.3 он содержит только разрешённые значения.
  Идентификаторы объектов нужны для разбора инцидентов. При попадании ПДн в URL зарегистрируйте
  инцидент и примените §14.5. Если в проекте как отклонение остался маршрут с учётными данными
  в query, обвязка удаляет его строку запроса перед журналированием.
- Задавайте уровень журналирования в конфигурации. Включайте `DEBUG` в эксплуатации только по согласованию.
- Экранируйте управляющие символы. Например, `\n` в значении может создать в журнале ложную строку.

## 16. Что делает общая обвязка (middleware)

Подключайте одну общую обвязку через шаблон сервиса. Так новые обработчики получат те же проверки.
В обвязке реализуйте следующие обязанности.

1. Примите `X-Request-Id`, если он содержит допустимый UUID. В остальных случаях создайте UUID v7
   и продолжите обработку. Верните `request_id` в заголовке и включите в контекст журнала.
2. Примите и продолжите `traceparent`. Верните его в ответе и передайте в исходящие вызовы и события.
3. Измерьте время обработки и укажите сервис и экземпляр (§9.2).
4. Примените входные ограничения §1.3. Проверьте заголовки, включая формат `Idempotency-Key`.
5. Извлеките учётные данные из объявленного источника. Проверьте `Origin` и состояние сессии.
   Определите, продлевает ли операция сессию (§8.2).
6. Для неизвестного параметра query верните `400`. Для недопустимого метода верните `405` с `Allow`.
7. Проверьте тело по закрытой схеме. Верните все нарушения одним ответом `422`. Переведите
   сообщения валидатора на язык продукта.
8. Преобразуйте исключения в Problem Details (§6).
9. Удалите заголовки, раскрывающие внутренние сведения. Установите обязательные заголовки (§9)
   и заголовки безопасности (§14.3).
10. Определите адрес клиента по правилам доверенных прокси. Примените лимиты.
11. Выполните все проверки и действия для идемпотентности (§10).

## 17. Повторы на стороне клиента

Используйте одну политику повторов для всех клиентов продукта.

- Автоматически повторяйте только чтение (`GET`, `search`, `count`) и изменяющие операции
  с `Idempotency-Key`. Автоматический повтор изменяющей операции без ключа запрещён.
- Допускается не более трёх попыток. Используйте задержки 0,5 с, 1 с и 2 с с разбросом ±20 %,
  чтобы клиенты не создавали одновременный пик нагрузки. Если дан `Retry-After`, всегда
  используйте его значение вместо расчётной задержки.
- Для `4xx` политика повторов допускает только `429`. Для обновления просроченного токена
  применяется отдельный сценарий §8.1.
- При `session_expired` приостановите всю очередь и сохраните её содержимое. После повторного
  входа продолжите обработку.
- После исчерпания попыток покажите ошибку и кнопку для ручного повтора.

## 18. Контракт

Храните OpenAPI 3.x в репозитории контрактов. Описывайте операции до реализации или одновременно
с ней. Генерируйте клиентов из контракта. Расхождение фактического ответа со спецификацией
считайте дефектом сервера.

Для каждой операции укажите:

- путь и метод, схему запроса с `additionalProperties: false`, схему успеха со всеми полями;
- все коды состояния, ссылку на общий компонент ошибки и обязательные заголовки;
- значение по умолчанию и максимум `limit`, закрытый список `expand`;
- необходимость `Idempotency-Key` или `If-Match`, класс активности (`always` или `on_marker`)
  и признак наличия ПДн в ответе.

Опишите `Problem`, `ValidationProblem`, `Page`, параметры пагинации и общие заголовки
как переиспользуемые компоненты. Ведите каталог `code` и `type` как часть контракта.
Клиент выбирает действие только по объявленным машинным значениям.

В CI проверьте имена параметров пути и query по §2.3 и формат UUID у `{id}`. Проверьте
объект на верхнем уровне, ключи и перечисления в `snake_case` и отсутствие `total` в страницах.
Проверьте обязательные заголовки, включая `Retry-After` у `429` и `503`.
Для каждого `4xx` и `5xx` проверьте ссылку на общий `Problem`.

## 19. Отклонения

В документации продукта ведите таблицу «Отклонения от конвенции по API». Для каждого отклонения
укажите правило, принятое решение, причину, цену и условие снятия. Объясните, зачем продукту
нужно это решение. Если отклонение не записано, верните изменение на доработку.

Примеры отклонений:

- Версия в заголовке для продукта, который поставляет клиент и сервер одним артефактом (§2.1).
- Cookie-сессия для страницы или `EventSource` при выполнении условий §1.2.
- Один процесс без распределённой трассировки опускает набор заголовков §9.2.
- Поля `_label` дополняют машинные значения (§11).
- Все чтения чувствительного ресурса идут через `POST .../search` (§2.3).
- Локальный процесс слушает только loopback и принимает соединения без TLS (§1.1).

- [ ] Путь использует /api/v<major>/ и имена в snake_case латиницей. Вложенность не превышает двух ресурсов. Ресурс-одиночка указан без {id}.
- [ ] Переменные сегменты {id} имеют формат UUID. Путь и query не содержат ПДн, идентификаторов субъектов, секретов и значимых естественных ключей.
- [ ] Фильтры по ПДн передаются в теле POST .../search. GET читает без тела и побочных эффектов. Доменное действие использует отдельный POST.
- [ ] Соединения защищены TLS с исключением для loopback. Учётные данные поступают только из объявленного источника. Cookie и Origin проверены по §1.2 и §14.2.
- [ ] Неизвестный параметр query даёт 400, лишнее поле тела — 422. Сервис возвращает все нарушения в errors[] с полным путём field.
- [ ] Ошибки соответствуют RFC 9457. Указаны type в формате URN, code, request_id и шаблон instance. Внутренние сведения и ПДн исключены.
- [ ] 2xx означает успех. У 201 есть id и Location, у 202 — задача, у 204 — диагностические заголовки. На чужой объект сервис возвращает 404.
- [ ] Каждый ответ содержит X-Request-Id и Cache-Control. При 429 и 503 есть Retry-After. GET ресурса возвращает ETag.
- [ ] Версионируемый ресурс требует If-Match. Отсутствие заголовка даёт 428, несовпадение — 412.
- [ ] Контракт повторяемого изменяющего POST объявляет Idempotency-Key или механизм §10.3. Повторы ключа обработаны по §10.2.
- [ ] Страница содержит items, next_cursor и has_more. Поле total исключено. Предел limit указан в контракте. Права ограничивают выборку.
- [ ] Момент _at заканчивается на Z. Дата _on, UUID v7, строковые деньги и количества, перечисления snake_case соответствуют §11.
- [ ] Вложенность объекта не превышает трёх уровней. Связи передаются ссылками. Значения expand перечислены. Неограниченные коллекции вынесены в подресурсы.
- [ ] Ответы с ПДн исключены из внешних кэшей. Для списков с ПДн действует пониженный максимум limit.
- [ ] Тела запросов не журналируются без согласования. Каждая строка содержит request_id. Уровень задаёт конфигурация.
