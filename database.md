# Конвенция по организации базы данных

**Редакция 2.3, 2026-11-28.** Конвенция принята 2026-09-06. Применяйте её при проектировании
и ревью реляционной базы данных (БД). Правила охватывают серверные базы, например PostgreSQL,
и встраиваемые базы, например SQLite и DuckDB.

Дайте ссылку на эту конвенцию в документе схемы. Если проекту требуется другое решение,
обоснуйте его и согласуйте на ревью (§16). Если изменение нарушает правило и отклонение
не согласовано, верните изменение на доработку.

Единые правила для ключей, авторства и времени позволяют добавить новый источник записей
без перенумерации строк и потери истории. При проверке типа данных сверьте схему, формат API
и примеры в соответствующем разделе.

## 1. Время

Храните моменты времени в UTC. Имя колонки заканчивайте на `_at`, например `created_at`,
`occurred_at`, `expires_at` или `synced_at`. Синхронизируйте часы серверов по NTP.
Тогда записи из разных часовых поясов можно сопоставить по времени события.

**Схема.** Используйте тип с часовым поясом. Тип без пояса может отбросить смещение при записи.
В PostgreSQL используйте `timestamptz`, в DuckDB — `TIMESTAMPTZ`. Установите пояс сессий приложения
в `UTC`. Выбирайте секунды или доли секунды с точностью, которая нужна продукту.

**SQLite.** Храните целое число секунд Unix (UTC) в колонке типа `INTEGER` с суффиксом `_at`.
Оформите отклонение по §16. Для чтения создайте представление с `datetime(x, 'unixepoch')`.

**Отображение.** Для показа человеку используйте пояс из его профиля. Если в профиле нет пояса,
возьмите его из настроек приложения. При ручном просмотре БД или логов можно явно выбрать
пояс, например `Europe/Moscow`. Если для учёта важен пояс склада, филиала или прибора,
сохраните имя зоны IANA в отдельном поле, например `Asia/Yekaterinburg`.

**API.** Принимайте значения со смещением и приводите их к UTC. Передавайте моменты в формате
ISO 8601 с окончанием `Z`. Выберите для всего проекта одну точность вывода — секунды или миллисекунды.

Верно: `issued_at TIMESTAMPTZ NOT NULL` → `"issued_at": "2026-08-01T09:00:00Z"`.
Неверно: `issued_date TIMESTAMP NOT NULL` — пояса нет, суффикса нет; `"issued_at":
"2026-08-01T12:00:00+03:00"` — смещение в исходящем контракте; `"issued_at": "01.08.2026, 12:00"` —
экранный формат в данных.

## 2. Календарные даты

Храните дату документа, поставки или отчёта в колонке типа `DATE`. Завершайте имя колонки
суффиксом `_on`, например `signed_on`, `delivery_on` или `day_on`. Календарный день одинаков
для читателей из разных часовых поясов. Если записать его как момент `00:00`, при переводе
в другой пояс читатель может увидеть предыдущий день.

Если вы вычисляете дату из момента времени, укажите пояс расчёта в документе схемы и в метаданных БД.
При смене пояса пересчитайте производные даты.

**API.** Передавайте дату строкой `YYYY-MM-DD` без времени, `Z` и смещения.

Верно: `accepted_on DATE NOT NULL` → `"accepted_on": "2026-08-01"`.
Неверно: `accepted_at TIMESTAMPTZ` для календарного дня приёмки; `day TEXT` в произвольном формате.

## 3. Идентификаторы и ключи

Для первичного ключа каждой таблицы используйте UUID версии 7. Ключ создаёт приложение через
общий генератор из разделяемой библиотеки. Исключите автоинкремент, последовательности, UUID v4
и составные первичные ключи. Формы служебных таблиц описаны в §6 и §11.

UUID занимает 16 байт. Клиент, агент синхронизации и импорт могут создавать ключи локально
без общей службы нумерации. Метка времени в старших битах UUID v7 группирует новые ключи
в конце индекса и позволяет использовать `id` для курсорной пагинации. По ключу можно оценить
время его создания. Если эти сведения чувствительны, заведите отдельный непрозрачный публичный код (§3.3).

**Схема.** Используйте тип `UUID`. Для SQLite выберите `BLOB(16)` или текст из 36 символов
и оформите отклонение по §16. Приложение передаёт `id` при вставке. Серверный `DEFAULT` для `id` запрещён.

Задайте естественную уникальность отдельным ограничением `UNIQUE` по нормализованному атрибуту
или группе атрибутов, например `email`, `path` или `(device_id, channel)`.
Закрепите нормализацию в `CHECK`, например `email = lower(email)`.

### 3.1. Факты и временные ряды

Для показаний, замеров и событий от фиксированного источника используйте тот же `id UUID v7`.
Дополнительно задайте `UNIQUE (измерение, момент)`, например `(sensor_id, measured_at)`.
Используйте пару для повторных вставок (§11) и выборок по диапазону. Единый первичный ключ
сохраняет общие правила для ссылок, удаления и пагинации. Дополнительный ключ занимает 16 байт на строку. При миллиардах строк используйте партиционирование.

### 3.2. Ключи внешних систем

Храните ключи сторонних систем в таблице соответствий
`external_ref (id, entity_type, entity_id, system, external_key)`. Задайте оба ограничения:
`UNIQUE (system, external_key)` и `UNIQUE (entity_type, entity_id, system)`. Тогда сущность может
иметь по одному соответствию в нескольких системах. Замена поставщика не потребует менять таблицу сущности.

Собственные атрибуты сущности, например почту или путь каталога, храните в её таблице.
Для естественного ключа применяйте нормализацию и `UNIQUE`.

### 3.3. В API

Передавайте UUID строкой со строчными буквами и дефисами. Проверяйте версию только у ключей
своей системы. Для идентификатора субъекта внешней системы аутентификации допускайте UUID любой версии.

Показывайте пользователю номер или название сущности с собственной нумерацией. Первичный ключ
используйте в адресе страницы и служебных панелях.

Верно: `id UUID PRIMARY KEY` со значением из общей библиотеки; `email VARCHAR NOT NULL UNIQUE CHECK
(email = lower(email))`; `UNIQUE (sensor_id, measured_at)` у ряда.
Неверно: `id BIGSERIAL PRIMARY KEY`; `id UUID DEFAULT gen_random_uuid()` — и v4, и второй источник;
`crm_code VARCHAR(30)` внутри сущности; составной первичный ключ вместо `id` плюс `UNIQUE`.

## 4. Перечисления и статусы

Используйте одни и те же значения перечислений в БД, API, событиях и коде. Пишите их латиницей
в `snake_case`, например `in_progress`, `awaiting_acceptance` или `http_429`. Кириллица и числовые
коды для этих значений запрещены. Подпись для пользователя берите из общего словаря приложения.
Тогда смена подписи не потребует миграции данных.

**Закрытый список.** Храните значение в `VARCHAR` с ограничением `CHECK (col IN (...))`.
Нативный `ENUM` запрещён. Изменение нативного списка зависит от движка, а ограничение `CHECK`
можно заменить и восстановить миграцией. Например, добавление значения через `ALTER TYPE`
в PostgreSQL требует учитывать границы транзакции. В DuckDB для изменения нативного списка может
потребоваться пересоздать зависимые колонки. В SQLite нативного перечисления нет. Запишите полный список один раз в документе схемы.
Скопируйте его в DDL и проверьте тестом, что документ, ограничение и код задают одинаковые значения.

**Редактируемый список.** Если пользователь или администратор меняет категории, теги или статусы,
используйте отдельную таблицу-справочник.

**API.** Передавайте ту же строку, например `"status": "awaiting_acceptance"`.
Согласуйте новое значение с потребителями. Удаление значения нарушает совместимость.

Верно: `stage VARCHAR(32) NOT NULL CHECK (stage IN ('new','in_review','approved','declined'))`.
Неверно: `status ENUM(...)`; `"status": "Ожидает приёмки"`; `"status": "AwaitingAcceptance"`; `"status": 7`.

## 5. Скалярные типы

| Значение | Правило |
|---|---|
| Логический признак | Используйте `BOOLEAN`. Записи `0/1`, `'Y'/'N'` и `NULL` в значении «нет» запрещены. |
| Деньги | Храните сумму в `DECIMAL(p, s)`, а код валюты ISO 4217 — в отдельной колонке. Типы `DOUBLE` и `FLOAT` могут потерять точность. В API передавайте сумму строкой, например `"1234.50"`. |
| Количество | Используйте `DECIMAL` с заданной точностью. Укажите единицу в отдельной колонке или имени, например `weight_kg`. |
| Процент | Храните целые проценты как целые числа с ограничением `CHECK (x BETWEEN 0 AND 100)`. Для дробных используйте `DECIMAL`. |
| Приближённое измерение | Используйте плавающую точку только там, где допустима погрешность, например для координат, задержки или показания датчика. |
| Строка | Используйте `VARCHAR`. Кроме перечислений, не задавайте произвольную длину. Выразите предметное ограничение через `CHECK`. По умолчанию задавайте `NOT NULL`. Если значение может отсутствовать, храните `NULL`. Пустая строка означает отдельное значение. |
| ФИО и адрес | Разделите ФИО на `last_name`, `first_name` и `middle_name NULL`. Формируйте «Иванов И. И.» при показе. Храните адрес по частям. Для обоих типов применяйте §13. |
| Телефон | Нормализуйте номер по E.164, например `+79161234567`. Формат для чтения задаёт интерфейс. |
| Длительность | Храните целое число с единицей в имени (`duration_sec`, суффиксы `_sec` и `_ms`). Для интервала задайте две колонки моментов (§7). |
| Данные переменной структуры | Используйте JSON только для таких данных, как тело события или исходный ответ внешней системы. Поля для поиска, сортировки и расчётов храните в колонках. |
| Бинарные данные | Поместите содержимое во внешнее хранилище. Сохраните в БД ключ объекта и контрольную сумму. |
| Секреты и токены | Исключите их из БД во всех представлениях (§14). |

## 6. Обязательные колонки

В каждую таблицу предметной области включите служебные колонки.

| Колонка | Что записать |
|---|---|
| `id UUID PRIMARY KEY` | UUID v7 из приложения (§3). |
| `created_at TIMESTAMPTZ NOT NULL` | Момент создания строки. |
| `updated_at TIMESTAMPTZ NOT NULL` | Момент последнего изменения. Обновляйте при каждой правке. |
| `deleted_at TIMESTAMPTZ NULL` | Момент мягкого удаления там, где оно применяется (§8). |
| `created_by UUID NOT NULL`, `updated_by UUID NOT NULL` | Идентификаторы автора создания и последней правки. Используйте субъект из проверенного токена или идентичность сервиса, агента либо самого процесса. |

Даже если строки создаёт один процесс, записывайте его идентификатор. Нулевое значение лишает
запись сведений об источнике. Добавляйте прикладные моменты `first_seen_at`, `last_seen_at` и `synced_at`
к служебному набору. Так можно восстановить авторство и время каждой правки.

**Исключение.** Для ключей идемпотентности, обработанных событий, outbox, метаданных схемы
и промежуточных таблиц (staging) используйте служебные схемы из §11 и документа проекта.
Список исключений закрыт. Новую служебную таблицу оформите по §16.

## 7. Интервалы и открытые записи

Храните начало и конец интервала в `started_at` и `ended_at`. Пока интервал открыт, оставляйте
`ended_at` равным `NULL`. Задайте `CHECK (ended_at IS NULL OR ended_at >= started_at)`.
При смене состояния закройте старую запись и откройте новую в одной транзакции. Так сохранится
история состояний.

Если у сущности может быть только один открытый интервал, закрепите это ограничение частичным
уникальным индексом. Например, для текущей смены сотрудника используйте следующий индекс.

```sql
CREATE UNIQUE INDEX shift_open_uidx ON shift (employee_id) WHERE ended_at IS NULL AND deleted_at IS NULL;
```

PostgreSQL и SQLite поддерживают частичные индексы. В DuckDB ограничение проверяет единственный
владелец записей в той же транзакции. Оформите отклонение по §16. Тест должен получить пустой
результат запроса `SELECT key FROM t WHERE ended_at IS NULL GROUP BY key HAVING count(*) > 1`.

## 8. Удаление

Если строка участвует в учёте или на неё ссылаются другие строки, установите `deleted_at`.
В каждую выборку текущего состояния включайте `deleted_at IS NULL`. Применяйте одно поле
и при удалении пользователем, и при исчезновении объекта из источника. Если нужна причина,
храните её в отдельной колонке `deleted_reason` со значениями перечисления (§4).

Для таблиц с мягким удалением задавайте частичные уникальные индексы с условием `deleted_at IS NULL`.
Тогда код или номер можно использовать снова. Если движок не поддерживает частичные индексы,
обеспечьте уникальность в коде и оформите отклонение по §16.

Физическое удаление допускается для журналов и кэшей по сроку хранения (§12), для служебных
таблиц механизмов и по требованиям к удалению персональных данных (§13.6). Опишите команды
и порядок удаления зависимых строк в документе схемы. Покройте этот порядок тестом даже
при наличии каскадов в движке. DuckDB не поддерживает действия `ON DELETE`.
Если историческая строка принадлежит окружению удаляемой сущности, сохраните строку и уберите ссылку.

| индекс | `<таблица>_<колонки>_idx`, уникальный — `_uidx` | `shift_open_uidx` |
| ограничение | `<таблица>_<колонки>_<uq\|ck\|fk>` | `limit_window_account_kind_model_uq` |

Используйте только общепринятые сокращения, например `id`, `sec`, `ms`, `tz`, `dir`, `url`.
Исключите `usr`, `cnt` и `dt`. Запрет на зарезервированные слова действует и для имён в кавычках.
Для `at`, `user`, `order` и `end` выберите предметные имена, например `measured_at`,
`app_user`, `purchase_order` и `ended_at`.

## 10. Запись данных

- Выполняйте бизнес-операцию в одной транзакции. Включите журнал, факты, смену интервалов,
  обновление справочников и запись в outbox (§11). Тогда сбой не оставит часть изменений на диске.
- При массовой записи используйте Appender или `COPY` для загрузки в `stage_*`. Перенесите
  строки в целевую таблицу одним `INSERT … SELECT`. Построчный `INSERT` создаёт накладные расходы на каждую запись. Для единичной строки допустим точечный `UPDATE`.
- Передавайте значения в SQL только параметрами. Выбирайте имена таблиц из закрытого списка в коде.
- Для встраиваемой БД закрепите соединение за одним потоком или файбером. Остальные отправляют
  ему сообщения. Если язык позволяет, выразите это ограничение типом. Для серверной БД используйте
  пул соединений с пределом размера и таймаутом ожидания.
- Если движок ведёт отдельный журнал, выполняйте checkpoint после записи. Это даёт целостную копию
  основного файла на диске.
- Обновляйте `updated_at` и `updated_by` вместе с данными. Для этого используйте триггер или слой доступа.

## 11. Идемпотентность и надёжная доставка

Обеспечьте безопасный повтор записи, входящей команды и обработки события. Повтор возможен
после таймаута клиента, повторной доставки брокером или перезапуска агента в середине пакета.

### 11.1. Идемпотентная запись

- При импорте сущности или строки справочника используйте `INSERT … ON CONFLICT (<естественный UNIQUE>) DO UPDATE SET …, updated_at = excluded.updated_at, updated_by = excluded.updated_by`.
  Повторный импорт обновит ту же запись.
- Для факта используйте `INSERT … ON CONFLICT (измерение, момент) DO NOTHING`. Повторная доставка
  того же замера сохранит прежнее состояние.
- При получении сообщения о смене интервала сравните новое состояние с открытой записью.
  Выполняйте переход по §7 только при различии.

### 11.2. Ключ идемпотентности входящих команд

Для входящего изменяющего сообщения клиент создаёт ключ идемпотентности (UUID) один раз на команду.
Для HTTP-операции используйте UUID v7, если контракт требует `Idempotency-Key`.
При каждой попытке клиент передаёт исходный ключ. Сервер ищет запись по паре `(actor, key)`.
Поле `actor` учитывает издателя токена и субъект. Разные субъекты могут независимо использовать один ключ.

```sql
CREATE TABLE idempotency_key (
  actor         VARCHAR NOT NULL,                 -- издатель токена и субъект
  key           UUID NOT NULL,                    -- ключ клиента
  request_hash  VARCHAR NOT NULL,                 -- для HTTP: хэш пути операции и исходных байтов тела
  response_code SMALLINT NOT NULL,
  response_body JSON,
  created_at    TIMESTAMPTZ NOT NULL,
  expires_at    TIMESTAMPTZ NOT NULL,             -- конец окна хранения
  PRIMARY KEY (actor, key)
);
```

Проверьте ключ, выполните команду и запишите успешный результат в одной транзакции.
Для HTTP вычисляйте отпечаток по пути операции и исходным байтам тела без нормализации JSON.
Сохраняйте только ответы `2xx`. При ошибке освободите ключ.

Для повтора с той же парой `(actor, key)` применяйте §10.2 [конвенции по HTTP API](api.md):

- Если первый запрос ещё выполняется, верните `409 idempotency_in_progress` и заголовок `Retry-After`.
- Если ответ сохранён и отпечаток совпал, верните сохранённый ответ с `X-Idempotent-Replay: true`.
- Если ответ сохранён и отпечаток отличается, верните `409 conflict`.

Задайте окно хранения в настройках с запасом сверх максимального срока повтора клиентской очереди.

### 11.3. Дедупликация у потребителя событий

Сохраняйте идентификаторы обработанных событий. Если потребитель уже обработал событие,
пропустите повтор.

```sql
CREATE TABLE processed_event (
  event_id     UUID PRIMARY KEY,
  consumer     VARCHAR NOT NULL,                  -- имя потребителя: у события их может быть несколько
  processed_at TIMESTAMPTZ NOT NULL,
  UNIQUE (event_id, consumer)
);
```

Запишите строку в `processed_event` и результат обработки в одной транзакции. Иначе при сбое
потребитель может потерять событие или применить его дважды.

### 11.4. Transactional outbox для исходящих событий

1. Запишите факт и событие в таблицу `outbox` в одной транзакции.
2. Отдельным процессом прочитайте ожидающее событие и опубликуйте его в брокере.
3. После публикации отметьте событие как отправленное.

Прямая публикация из бизнес-транзакции запрещена. Если публикация прошла до отката, потребитель
получит событие о несостоявшейся операции. Если процесс завершится после коммита и до прямой
публикации, событие потеряется.

```sql
CREATE TABLE outbox (
  id           UUID PRIMARY KEY,                  -- v7: порядок публикации совпадает с порядком создания
  event_type   VARCHAR NOT NULL,                  -- <модуль>.<сущность>.<действие>
  aggregate_id UUID NOT NULL,                     -- ключ маршрутизации / партиции
  payload      JSON NOT NULL,                     -- конверт события целиком
  created_at   TIMESTAMPTZ NOT NULL,
  published_at TIMESTAMPTZ NULL                   -- NULL = ещё не отправлено
);
CREATE INDEX outbox_pending_idx ON outbox (created_at) WHERE published_at IS NULL;
```

Удаляйте отправленные строки по сроку хранения (§12). Outbox обеспечивает доставку не менее
одного раза. Потребитель должен исключить повторное применение события по §11.3.

### 11.5. Тесты

- Вызовите каждую изменяющую операцию дважды. Проверьте, что второй вызов возвращает тот же ответ
  и сохраняет состояние после первого вызова.
- Доставьте каждому потребителю одно событие дважды. Проверьте, что эффект возник один раз.
- Для каждой транзакции с outbox имитируйте сбой между записью факта и публикацией. Факт и запись
  о событии должны либо сохраниться вместе, либо вместе отсутствовать.

## 12. Ретенция и свёртки

Задайте срок хранения каждого ряда, журнала и служебной таблицы в настройках. Сущности
и интервалы, которые образуют историю, храните бессрочно. Для персональных данных применяйте §13.6.

1. Пока исходные данные доступны и движок быстро вычисляет свёртку, рассчитывайте её при чтении.
2. Перед удалением исходных данных за период сохраните свёртку одной операцией
   `INSERT … SELECT … ON CONFLICT DO UPDATE`. Для календарного дня используйте пояс из метаданных БД.
   При смене пояса пересчитайте свёртки за периоды с доступными исходными данными и обновите записи.
3. Удаляйте строки порциями по колонке момента с помощью `DELETE`. Затем выполняйте checkpoint.
   Применяйте `VACUUM` или пересобирайте файл при его разрастании.
4. Для очистки `idempotency_key` используйте `expires_at`. Для `processed_event` и `outbox`
   используйте окна хранения из настроек.

## 13. Персональные данные (ПДн)

Относите к персональным данным (ПДн) сведения, по которым можно определить человека напрямую
или в сочетании с другими данными. Примеры — ФИО, почта, телефон, адрес, дата рождения, документы,
внешние идентификаторы, фотографии и точные координаты. Учитывайте технические данные, связанные
с человеком, например IP-адрес, идентификатор устройства или путь домашнего каталога с именем пользователя.

Укажите в документе схемы для каждой такой колонки `pdn: yes`, категорию, законное основание
и срок хранения. По умолчанию колонка без отметки считается свободной от ПДн. Если в ней есть,
например, почта или телефон, ревьюер должен потребовать исправления классификации.

Учитывайте применимые требования к ПДн при проектировании схемы, ролей, журналов и резервных
копий. Это касается как российских требований, так и GDPR, когда продукт работает в его сфере действия.

### 13.1. Минимизация

Для каждого поля с ПДн укажите в документе схемы, какой функции оно нужно. Храните значение
только на необходимый срок. Удалите поля без назначения. Например, если для входа нужна только
почта, исключите ФИО, телефон и адрес из сбора и хранения, даже если внешний источник их передаёт.

### 13.2. Изоляция

Разместите ПДн в отдельной схеме `pdn`. Для движка без схем используйте префикс таблиц `pdn_`.
Связывайте ПДн с основными сущностями по `id`. В аналитике, журналах и свёртках используйте только
идентификатор человека. Например, стройте отчёт по `account_id`. Если для показа нужна почта,
присоедините таблицу ПДн с правами читателя.

Для схемы `pdn` в PostgreSQL назначьте отдельного владельца. Для SQLite и DuckDB используйте
отдельный файл `<приложение>-pdn.<ext>` с более строгими правами. Подключайте его через `ATTACH`.

### 13.3. Шифрование

Шифруйте колонки с ПДн в приложении. Берите ключ из хранилища секретов, например Vault transit,
KMS или системного хранилища ключей. База, репозиторий и конфигурация рядом с базой не должны
содержать ключ. Резервная копия, дамп и скопированный файл должны оставаться нечитаемыми без ключа.
При ротации перешифруйте данные по документированной процедуре.

Если нужен поиск, сохраните рядом детерминированный хэш с солью, например `email_hash`.
Индексируйте только хэш.

Для серверной БД шифрование в приложении обязательно. Для однопользовательской встраиваемой
БД допустим также зашифрованный файл (DuckDB `ENCRYPTION_KEY` или SQLCipher для SQLite).
Храните ключ в системном хранилище учётных данных.

### 13.4. Доступ и аудит

Выделите для `pdn` отдельную роль БД с минимальными правами. Выдавайте её только сервисам,
которым нужны ПДн. При каждом чтении или изменении ПДн из приложения запишите в аудит субъект
из токена, сущность, поля, время и операцию. Используйте идентификаторы. Значения ПДн в аудит не включайте.

Для массовой выборки, например экспорта или отчёта, определите отдельную операцию.
Назначьте ей отдельное право и регистрируйте каждый вызов в аудите.

### 13.5. ПДн вне таблиц

- **Логи.** Записывайте идентификаторы. Исключите почту, ФИО, телефоны, пути с именем пользователя
  и другие ПДн. Маскируйте текст ошибки до записи.
- **События и очереди.** Для ссылки на человека передавайте только идентификатор. Если потребителю
  нужна почта, он запрашивает её с собственными правами.
- **URL и заголовки.** Передавайте ПДн и идентификаторы записей о людях в теле запроса.
  Путь и строка запроса попадают в журналы, историю браузера и `Referer` даже при TLS.
- **Экспорт.** По умолчанию маскируйте значения, например `i***@example.com`. Для полной выгрузки
  требуйте отдельное право, регистрируйте операцию в аудите и шифруйте файл.
- **Тесты.** Используйте синтетические данные, например `user1@example.com` и вымышленные ФИО.
  Копирование продуктивных данных в тесты запрещено. Обезличенную копию можно использовать
  только по документированной процедуре псевдонимизации.
- **Резервные копии.** Шифруйте их ключами того же класса. Предельный срок хранения равен
  сроку хранения данных плюс окно восстановления.

### 13.6. Сроки и право на удаление

Укажите срок и основание хранения каждого поля с ПДн. По истечении срока автоматически
удаляйте или обезличивайте данные по правилам ретенции (§12).

Реализуйте удаление одной командой `forget <субъект>`. Опишите порядок в документе схемы.
Физически удалите строки с ПДн. Сохраните строки аналитики и истории, удалив связь с человеком.
Если нужно сохранить агрегат, можно заменить связь псевдонимом. Покройте процедуру тестом
с обратной пробой. После выполнения команды поиск по всем хранилищам, логам и резервным копиям
в пределах окна не должен находить субъекта.

Если таблица использует мягкое удаление (§8), обезличьте поля с ПДн. Сама отметка `deleted_at`
сохраняет содержимое строки.

### 13.7. Реестр ПДн

Ведите в документе схемы таблицу «Реестр ПДн». Для каждой колонки укажите:

- класс данных, категорию ПДн и функцию продукта;
- законное основание и срок хранения;
- способ защиты (схему, шифрование и роль) и способ удаления;
- все места, куда попадает значение: ответы конкретных операций API, экспорты, события, кэши и журналы.

Обновляйте реестр вместе с колонкой. Если реестр не обновлён, верните изменение на доработку.
Используйте общий для схемы и HTTP-контракта закрытый список классов: `none`, `pii`,
`subject_id` и `secret`. Класс `subject_id` означает идентификатор, однозначно связывающий запись
с человеком. Правила для контракта приведены в §14.5 [конвенции по API](api.md).

Выводите из реестра запреты для URL, пределы выборки, правила кэширования и маскирования в экспортах
и журналах. Относите спорные признаки к `pii` заранее. Это касается сетевого адреса, идентификатора
устройства, геолокации и логина. Назначьте владельца и срок регулярной сверки реестра
с действующими требованиями законодательства.

## 14. Безопасность данных вне ПДн

- Исключите токены, ключи и пароли из колонок, JSON и текстов ошибок. Перед записью ограничьте
  длину текста ошибки и замените строки, похожие на токен, на `***`. Тест должен завершаться
  ошибкой, если находит секрет из тестового набора в файле БД или логах.
- Маскируйте секреты в версиях конфигурации и снимках настроек.
- Отключите автозагрузку расширений и телеметрию при сборке и для соединения. Проверьте
  с сетевой заглушкой, что за прогон база не сделала ни одного сетевого вызова.
- Для файлов встраиваемой БД используйте каталог данных пользователя и права `0600`. Исключите
  файлы из поисковой индексации. Копируйте базу вместе с журналом или после checkpoint.
- Для соединения с серверной БД используйте только TLS и роли с минимальными правами. Запретите
  приложению доступ от имени суперпользователя.
- Периодически проверяйте резервные копии пробным восстановлением.

## 15. Миграции

1. Храните пронумерованные миграции в репозитории проекта. Меняйте схему только такими миграциями.
   В таблице метаданных фиксируйте версию схемы, версию движка и набор расширений.
2. Перед применением автоматически создайте резервную копию. Выполняйте каждую миграцию в отдельной
   транзакции при старте или отдельной командой. Если версия схемы новее поддерживаемой, приложение
   должно остановить запуск и сообщить причину.
3. Проверьте миграцию на непустой БД. Предусмотрите обратную миграцию. Если она невозможна,
   объясните причину и восстанавливайте БД из копии, созданной перед изменением.
4. При несовместимом изменении типа, значения или состава колонок используйте две версии.
   Сначала добавьте новую структуру и перенесите данные. В следующей версии удалите старую структуру.
   Во время развёртывания предыдущая версия приложения должна работать с БД.
5. Прочитайте сгенерированную миграцию целиком и передайте её на ревью. Проверьте индексы,
   значения по умолчанию и переименования. Генератор может предложить удалить колонку, для которой
   нужен перенос в два шага. Автор отвечает за сгенерированную миграцию.
6. Меняйте схему и контракт API вместе. Сначала определите контракт, затем приведите схему в соответствие.

## 16. Отклонения

Если правило неприменимо, оформите архитектурное решение (ADR) в каталоге решений проекта.
Если проект не ведёт ADR, добавьте запись в раздел «Отклонения от конвенции» в документе схемы.

Укажите правило, причину отклонения, рассмотренные варианты, принятое решение и его цену.
Передайте запись на ревью вместе с кодом. Отклонение действует после согласования. Если решение
подходит всем проектам и оправдало себя на практике, внесите его в конвенцию. Добавьте в запись ссылку на изменение.

Примеры причин — обязательный формат партнёра, объём данных или ограничение движка.
Типичные примеры решений:

- SQLite хранит секунды Unix в `INTEGER`, а UUID — в `BLOB(16)`.
- Для DuckDB приложение обеспечивает единственность открытого интервала и порядок удаления
  зависимых строк. Тесты проверяют оба правила.
- Однопользовательское приложение использует один файл вместо отдельной схемы `pdn`.
  Оно ведёт реестр, шифрует файл и применяет правила журналирования ПДн.

## 17. Чек-лист ревью схемы

- [ ] Моменты имеют суффикс `_at` и тип с поясом. Сессии приложения работают в UTC. Исходящий API использует `Z`. У календарных дат тип `DATE` и суффикс `_on`.
- [ ] Приложение выдаёт UUID v7. У `id` нет серверного `DEFAULT`. Естественный ключ защищён `UNIQUE`, нормализация — `CHECK`. У фактов есть `UNIQUE (измерение, момент)`.
- [ ] Идентификаторы сторонних систем хранятся в `external_ref`.
- [ ] Закрытые перечисления используют `VARCHAR`, `CHECK` и латиницу `snake_case`. Списки сверены с документом схемы и кодом.
- [ ] Флаги имеют тип `BOOLEAN`, деньги и точные доли — `DECIMAL`. Целые проценты ограничены `CHECK`. По умолчанию задан `NOT NULL`. ФИО и адрес хранятся по частям, телефон соответствует E.164.
- [ ] Есть служебные колонки §6, включая авторов и, где применимо, `deleted_at`. Исключения входят в закрытый список или согласованы.
- [ ] Порядок границ интервала проверяет `CHECK`. Для сущности с одним открытым интервалом действует ограничение §7.
- [ ] Текущие выборки исключают мягко удалённые строки. Уникальность учитывает `deleted_at`. Порядок физического удаления описан и проверен тестом.
- [ ] Имена соответствуют §9. Зарезервированные слова и нестандартные сокращения исключены.
- [ ] Запись использует транзакцию и параметры. Массовая запись идёт пакетами. `updated_at` и `updated_by` меняются вместе с данными.
- [ ] Повтор импорта, команды и события проверен тестами. Ключи, `processed_event` и `outbox` используются по §11. Сбой при публикации покрыт тестом.
- [ ] Сроки хранения заданы в настройках, пояс свёртки — в метаданных. Очистка охватывает служебные таблицы.
- [ ] Все колонки с ПДн внесены в реестр. Проверены изоляция, шифрование и доступ по §13. Аналитика использует идентификаторы. Логи, события, URL и тестовые данные проверены по §13.5.
- [ ] Срок и команда удаления ПДн описаны. Результат удаления проверен по §13.6.
- [ ] Секреты исключены из схемы и замаскированы в диагностике и фикстурах. База не обращается к сети. Резервную копию удалось восстановить.
- [ ] Миграция пронумерована и проверена на непустой БД после резервного копирования. Откат проверен или объяснён. Несовместимое изменение разбито на две версии. Сгенерированный файл прошёл ревью.
- [ ] Каждое отклонение согласовано и содержит причину и цену.
